# Проектирование базы данных

## 1. Назначение документа

Документ определяет логическую и физическую модель реляционной базы данных программного средства прогнозирования потребительского спроса.

В качестве СУБД используется PostgreSQL.

Модель данных разработана на основании:

- функциональных требований;
- пользовательских сценариев;
- архитектуры системы;
- REST API;
- требований к хранению исторических продаж и результатов прогнозирования.

Основными сущностями являются:

1. `User`;
2. `Product`;
3. `Sale`;
4. `Forecast`;
5. `ForecastValue`.

Структура приведена к третьей нормальной форме.

---

# 2. Общие принципы проектирования

При проектировании базы данных используются следующие принципы:

- каждая сущность хранится в отдельной таблице;
- каждая таблица имеет первичный ключ;
- связи реализуются с помощью внешних ключей;
- дублирование предметных данных минимизируется;
- ссылочная целостность обеспечивается средствами PostgreSQL;
- критические бизнес-ограничения дублируются на уровне БД там, где это целесообразно;
- часто используемые операции поиска поддерживаются индексами;
- результаты прогнозирования сохраняются независимо от последующих запусков модели.

В базе данных не должны храниться:

- пароли в открытом виде;
- JWT;
- секреты приложения;
- файлы обученных моделей;
- исходный код ML-компонента.

# 3. Сущность User

Таблица:

`users`

Назначение — хранение учётных записей пользователей системы.

| Поле | PostgreSQL | Ограничения | Назначение |
| --- | --- | --- | --- |
| id | BIGINT | PK, GENERATED | Идентификатор пользователя |
| name | VARCHAR(100) | NOT NULL | Имя пользователя |
| email | VARCHAR(255) | NOT NULL, UNIQUE | Уникальный логин |
| password_hash | VARCHAR(255) | NOT NULL | Хеш пароля |
| role | VARCHAR(20) | NOT NULL | Роль пользователя |
| created_at | TIMESTAMPTZ | NOT NULL | Дата создания |
| updated_at | TIMESTAMPTZ | NOT NULL | Дата изменения |

Допустимые значения `role`:

- `USER`;
- `ADMIN`.

Ограничение:

    CHECK (role IN ('USER', 'ADMIN'))

Поле `email` должно быть уникальным.

Пароль пользователя хранится только в поле `password_hash` после применения алгоритма хеширования.

---

# 4. Сущность Product

Таблица:

`products`

Представляет товар, для которого хранятся продажи и могут формироваться прогнозы.

| Поле | PostgreSQL | Ограничения | Назначение |
| --- | --- | --- | --- |
| id | BIGINT | PK, GENERATED | Идентификатор |
| sku | VARCHAR(64) | NOT NULL, UNIQUE | Уникальный код товара |
| name | VARCHAR(255) | NOT NULL | Наименование |
| category | VARCHAR(120) | NULL | Категория |
| created_at | TIMESTAMPTZ | NOT NULL | Дата создания |
| updated_at | TIMESTAMPTZ | NOT NULL | Дата изменения |

`sku` используется при:

- поиске товара;
- сопоставлении строк CSV;
- идентификации товара во внешних данных.

Наименование товара не используется как технический идентификатор.

---

# 5. Сущность Sale

Таблица:

`sales`

Представляет агрегированное количество проданных единиц конкретного товара за календарную дату.

Для текущей версии системы используется следующая гранулярность:

**один товар — одна дата — одно агрегированное значение продаж.**

Это упрощает построение временного ряда и исключает необходимость повторного агрегирования отдельных операций продажи при каждом прогнозировании.

| Поле | PostgreSQL | Ограничения | Назначение |
| --- | --- | --- | --- |
| id | BIGINT | PK, GENERATED | Идентификатор |
| product_id | BIGINT | NOT NULL, FK | Товар |
| sale_date | DATE | NOT NULL | Дата |
| quantity | INTEGER | NOT NULL | Количество проданных единиц |
| created_at | TIMESTAMPTZ | NOT NULL | Дата создания записи |

Внешний ключ:

    sales.product_id
        -> products.id

Правило удаления:

    ON DELETE RESTRICT

Количество должно удовлетворять:

    CHECK (quantity >= 0)

Комбинация:

    product_id + sale_date

должна быть уникальной.

Ограничение:

    UNIQUE (product_id, sale_date)

Если при импорте CSV обнаруживается несколько строк для одного товара и одной даты, они должны быть обработаны в соответствии с правилами импорта до сохранения итогового значения.

---

# 6. Сущность Forecast

Таблица:

`forecasts`

Представляет отдельный запуск прогнозирования.

| Поле | PostgreSQL | Ограничения | Назначение |
| --- | --- | --- | --- |
| id | BIGINT | PK, GENERATED | Идентификатор прогноза |
| user_id | BIGINT | NOT NULL, FK | Пользователь, инициировавший запуск |
| product_id | BIGINT | NOT NULL, FK | Прогнозируемый товар |
| forecast_horizon | INTEGER | NOT NULL | Горизонт прогнозирования |
| model_version | VARCHAR(100) | NOT NULL | Версия модели |
| status | VARCHAR(20) | NOT NULL | Состояние запуска |
| mae | NUMERIC(18,6) | NULL | MAE |
| rmse | NUMERIC(18,6) | NULL | RMSE |
| mape | NUMERIC(18,6) | NULL | MAPE |
| created_at | TIMESTAMPTZ | NOT NULL | Дата создания |
| started_at | TIMESTAMPTZ | NULL | Начало обработки |
| completed_at | TIMESTAMPTZ | NULL | Завершение |
| error_message | VARCHAR(1000) | NULL | Безопасное описание ошибки |

Внешние ключи:

    forecasts.user_id
        -> users.id

    forecasts.product_id
        -> products.id

Для обеих связей используется:

    ON DELETE RESTRICT

Допустимые значения `status`:

- `PENDING`;
- `PROCESSING`;
- `COMPLETED`;
- `FAILED`.

Ограничение:

    CHECK (
        status IN (
            'PENDING',
            'PROCESSING',
            'COMPLETED',
            'FAILED'
        )
    )

Горизонт должен быть положительным:

    CHECK (forecast_horizon > 0)

Показатели качества могут отсутствовать, если для соответствующего периода ещё невозможно выполнить сравнение с фактическими значениями.

---

# 7. Сущность ForecastValue

Таблица:

`forecast_values`

Содержит отдельные прогнозируемые значения, относящиеся к одному запуску.

| Поле | PostgreSQL | Ограничения | Назначение |
| --- | --- | --- | --- |
| id | BIGINT | PK, GENERATED | Идентификатор |
| forecast_id | BIGINT | NOT NULL, FK | Прогноз |
| forecast_date | DATE | NOT NULL | Дата прогнозируемого значения |
| predicted_quantity | NUMERIC(18,4) | NOT NULL | Прогнозируемый спрос |

Внешний ключ:

    forecast_values.forecast_id
        -> forecasts.id

Используется:

    ON DELETE CASCADE

Это оправдано тем, что `ForecastValue` не имеет самостоятельного смысла без родительского `Forecast`.

Для одного прогноза должна существовать только одна запись на конкретную дату:

    UNIQUE (forecast_id, forecast_date)

Прогнозируемое количество не должно быть отрицательным:

    CHECK (predicted_quantity >= 0)

---

# 8. Почему фактические значения не дублируются в ForecastValue

Фактический спрос уже хранится в таблице `sales`.

Поэтому поле вида:

`actual_quantity`

в `forecast_values` не добавляется.

Это предотвращает хранение одного и того же фактического значения одновременно:

- в `sales`;
- в `forecast_values`.

При необходимости сравнения прогнозного и фактического значения Backend сопоставляет:

- `forecast_values.forecast_date`;
- соответствующий `sale.sale_date`;
- один и тот же `product_id`.

Таким образом устраняется избыточность данных.

---

# 9. Связи сущностей

Основные отношения:

    User 1 -------- * Forecast

    Product 1 ----- * Sale

    Product 1 ----- * Forecast

    Forecast 1 ---- * ForecastValue

Расшифровка:

### User → Forecast

Один пользователь может создать множество прогнозов.

Каждый прогноз принадлежит одному пользователю.

### Product → Sale

Один товар может иметь множество исторических значений продаж.

Каждая запись Sale относится только к одному товару.

### Product → Forecast

Для одного товара может быть сформировано множество прогнозов.

Каждый прогноз строится для одного товара.

### Forecast → ForecastValue

Один запуск прогнозирования содержит несколько прогнозируемых значений.

Каждое значение относится к одному Forecast.

# 11. Нормализация

Структура приводится к третьей нормальной форме.

## 11.1. Первая нормальная форма

Все атрибуты являются атомарными.

Например, в `Product`:

    sku
    name
    category

хранят отдельные значения.

В одном поле не хранятся списки товаров, продаж или прогнозируемых дат.

Следовательно, требования 1НФ выполняются.

## 11.2. Вторая нормальная форма

Каждая таблица имеет однозначный первичный ключ.

Неключевые атрибуты зависят от полного первичного ключа.

Например:

`Sale.quantity`

зависит от конкретной записи продажи, а товар хранится через внешний ключ.

Данные товара не копируются в таблицу продаж.

Следовательно, частичные функциональные зависимости отсутствуют.

## 11.3. Третья нормальная форма

Неключевые атрибуты не должны зависеть друг от друга транзитивно.

Поэтому:

- данные пользователя хранятся только в `users`;
- данные товара хранятся только в `products`;
- данные продажи не содержат название товара;
- Forecast не хранит email пользователя;
- Forecast не хранит название или SKU товара;
- ForecastValue не дублирует характеристики Forecast;
- ForecastValue не дублирует фактические продажи.

Например, вместо:

    forecast_id
    product_id
    product_name
    product_category

в `ForecastValue` хранится только:

    forecast_id

а информация о товаре определяется через:

    Forecast
        -> Product

Таким образом транзитивное дублирование устраняется.

Модель соответствует третьей нормальной форме.

---

# 12. Первичные ключи

Для всех основных сущностей используются суррогатные числовые идентификаторы:

    BIGINT

Генерация выполняется средствами PostgreSQL.

Таблицы:

    users.id
    products.id
    sales.id
    forecasts.id
    forecast_values.id

Использование surrogate key позволяет не связывать внутреннюю идентичность записи с изменяемыми предметными атрибутами.

---

# 13. Внешние ключи

Определяются следующие внешние ключи:

    sales.product_id
        -> products.id

    forecasts.user_id
        -> users.id

    forecasts.product_id
        -> products.id

    forecast_values.forecast_id
        -> forecasts.id

Для `Product` и `User` используется `RESTRICT`, чтобы удаление сущности не приводило к потере связанных предметных данных.

Для `Forecast → ForecastValue` используется `CASCADE`, поскольку отдельное значение прогноза не существует без родительского запуска.

---

# 14. Уникальные ограничения

Используются:

    users.email

    products.sku

    sales(product_id, sale_date)

    forecast_values(forecast_id, forecast_date)

Это предотвращает:

- повторную регистрацию одного email;
- дублирование SKU;
- появление двух дневных значений продаж одного товара;
- появление нескольких прогнозных значений одного запуска на одну дату.

---

# 15. CHECK-ограничения

Необходимо определить как минимум:

    users.role IN ('USER', 'ADMIN')

    sales.quantity >= 0

    forecasts.forecast_horizon > 0

    forecasts.status IN (
        'PENDING',
        'PROCESSING',
        'COMPLETED',
        'FAILED'
    )

    forecast_values.predicted_quantity >= 0

При наличии дополнительных требований проверки могут быть расширены.

---

# 16. Индексы

PostgreSQL автоматически создаёт индексы для:

- PRIMARY KEY;
- UNIQUE.

Дополнительно необходимо создать индексы под основные сценарии чтения.

## 16.1. История продаж товара

    INDEX sales_product_date_idx
        ON sales(product_id, sale_date)

Используется при:

- просмотре продаж товара;
- фильтрации по диапазону;
- получении временного ряда для прогнозирования.

## 16.2. История прогнозов пользователя

    INDEX forecasts_user_created_idx
        ON forecasts(user_id, created_at DESC)

Используется для просмотра истории прогнозов пользователя.

## 16.3. Прогнозы товара

    INDEX forecasts_product_created_idx
        ON forecasts(product_id, created_at DESC)

Используется для:

- фильтрации истории;
- анализа прогнозов конкретного товара.

## 16.4. Значения прогноза

Уникальное ограничение:

    UNIQUE (forecast_id, forecast_date)

уже создаёт индекс, поэтому отдельный индекс на аналогичный набор полей не требуется.

## 16.5. Поиск по email и SKU

Отдельные индексы создавать не требуется, поскольку:

    UNIQUE users.email

и:

    UNIQUE products.sku

уже создают необходимые уникальные индексы.

---

# 17. Необязательные индексы

Не следует создавать индексы на каждое поле заранее.

Например, отдельный индекс на:

    products.category

необходим только в случае, если фильтрация по категории станет частым и подтверждённым сценарием.

Индексы увеличивают скорость чтения, но создают дополнительные затраты при записи и занимают место.

Поэтому дополнительные индексы должны добавляться на основании реальных запросов.

---

# 18. Правила удаления

## User

Удаление пользователя, для которого имеются Forecast, запрещается правилами ссылочной целостности.

Для будущего развития может быть введено логическое отключение пользователя вместо физического удаления.

## Product

Удаление товара запрещается, если существуют:

- Sale;
- Forecast.

Это предотвращает потерю истории.

## Sale

Продажи могут изменяться или удаляться только административным сценарием, если такой функционал будет предусмотрен.

Массовое случайное удаление через каскад Product запрещено.

## Forecast

При удалении Forecast связанные ForecastValue удаляются каскадно.

---

# 19. Временные данные

Для системных временных отметок используется:

    TIMESTAMPTZ

Это позволяет однозначно хранить момент времени независимо от часового пояса приложения.

Для предметной календарной даты продажи используется:

    DATE

Поскольку дневное значение продаж не требует хранения времени суток.

То же относится к:

    forecast_date

---

# 20. Числовые типы

Для фактического количества продаж используется:

    INTEGER

поскольку в текущей предметной модели количество проданных единиц является целым числом.

Для результата модели используется:

    NUMERIC(18,4)

поскольку нейросетевая модель может возвращать дробное прогнозируемое значение.

Метрики используют:

    NUMERIC(18,6)

для сохранения необходимой точности.

---

# 21. Модель хранения метрик

В текущей версии:

    mae
    rmse
    mape

хранятся непосредственно в `forecasts`.

Это не нарушает 3НФ, поскольку каждое значение функционально зависит непосредственно от конкретного Forecast.

Создание отдельной таблицы метрик для трёх фиксированных показателей в MVP не требуется.

Если в дальнейшем набор метрик станет динамическим, модель может быть расширена отдельной сущностью.

---

# 22. Версия ML-модели

Поле:

    forecasts.model_version

сохраняет версию модели, фактически использованную для получения результата.

Например:

    lstm-1.0.0

Это необходимо для:

- воспроизводимости;
- анализа предыдущих прогнозов;
- сравнения результатов разных версий модели.

Отдельная таблица моделей на текущем этапе не вводится, поскольку управление реестром моделей не входит в обязательный MVP.

# 25. Миграции

Создание и изменение физической схемы базы данных должно выполняться через механизм миграций.

Ручное изменение структуры рабочей базы без миграции не должно быть основным способом разработки.

Конкретный инструмент миграций определяется на этапе реализации Backend.

Миграции должны находиться под контролем Git.
