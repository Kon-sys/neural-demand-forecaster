# Проектирование базы данных

## 1. Назначение документа

Документ определяет логическую и физическую модель реляционной базы данных программного средства прогнозирования потребительского спроса.

В качестве СУБД используется PostgreSQL.

Модель данных разработана на основании:

- функциональных требований;
- пользовательских сценариев;
- архитектуры системы;
- REST API;
- требований к хранению исторических продаж и результатов прогнозирования;
- требований к профилям пользователей;
- требований к административному управлению пользователями;
- требований к организационной структуре.

Основными сущностями являются:

1. `Department`;
2. `Position`;
3. `User`;
4. `Product`;
5. `Sale`;
6. `Forecast`;
7. `ForecastValue`.

Структура приведена к третьей нормальной форме.

---

# 2. Общие принципы проектирования

При проектировании базы данных используются следующие принципы:

- каждая предметная сущность хранится в отдельной таблице;
- каждая таблица имеет первичный ключ;
- связи реализуются с помощью внешних ключей;
- дублирование предметных данных минимизируется;
- ссылочная целостность обеспечивается средствами PostgreSQL;
- критические бизнес-ограничения дополнительно проверяются Backend;
- часто используемые операции поиска поддерживаются индексами;
- результаты прогнозирования сохраняются независимо от последующих запусков модели;
- организационная принадлежность пользователя определяется через назначенную должность;
- должность не может существовать без подразделения.

В базе данных не должны храниться:

- пароли в открытом виде;
- JWT;
- секреты приложения;
- секретные ключи объектного хранилища;
- бинарные файлы фотографий профиля;
- файлы обученных моделей;
- исходный код ML-компонента.

Фотографии профиля пользователей хранятся во внешнем объектном хранилище.

В PostgreSQL сохраняется только URL изображения.

# 3. Сущность Department

Таблица:

    departments

Назначение — хранение справочника подразделений организации.

| Поле | PostgreSQL | Ограничения | Назначение |
| --- | --- | --- | --- |
| id | BIGINT | PK, GENERATED | Идентификатор подразделения |
| name | VARCHAR(150) | NOT NULL | Наименование подразделения |
| is_active | BOOLEAN | NOT NULL, DEFAULT TRUE | Доступность подразделения для новых назначений |
| created_at | TIMESTAMPTZ | NOT NULL | Дата создания |
| updated_at | TIMESTAMPTZ | NOT NULL | Дата последнего изменения |

Подразделение создаётся пользователем с ролью `ADMIN`.

Наименование подразделения не должно быть пустым.

Для предотвращения создания дублей без учёта регистра рекомендуется использовать функциональный уникальный индекс:

    CREATE UNIQUE INDEX departments_name_uq
        ON departments (LOWER(name));

Например, одновременное существование:

    Отдел разработки

и:

    отдел разработки

не допускается.

В рамках MVP подразделения не удаляются физически.

Для исключения подразделения из новых назначений используется:

    is_active = FALSE

Деактивированное подразделение:

- сохраняется в базе данных;
- сохраняет связанные должности;
- сохраняет существующие пользовательские назначения;
- не должно использоваться для новых назначений пользователей;
- не должно использоваться при создании новых активных организационных назначений.

# 4. Сущность Position

Таблица:

    positions

Назначение — хранение справочника должностей организации.

| Поле | PostgreSQL | Ограничения | Назначение |
| --- | --- | --- | --- |
| id | BIGINT | PK, GENERATED | Идентификатор должности |
| department_id | BIGINT | NOT NULL, FK | Подразделение, к которому относится должность |
| name | VARCHAR(150) | NOT NULL | Наименование должности |
| is_active | BOOLEAN | NOT NULL, DEFAULT TRUE | Доступность должности для новых назначений |
| created_at | TIMESTAMPTZ | NOT NULL | Дата создания |
| updated_at | TIMESTAMPTZ | NOT NULL | Дата последнего изменения |

Внешний ключ:

    positions.department_id
        -> departments.id

Правило удаления:

    ON DELETE RESTRICT

Поле:

    department_id

является обязательным.

Следовательно, создание должности без подразделения невозможно.

Каждая должность относится ровно к одному подразделению.

Например:

    Отдел разработки
        -> Junior Developer
        -> Middle Developer
        -> Senior Developer

    Отдел маркетинга
        -> Marketing Specialist
        -> Marketing Manager

Для предотвращения создания двух одинаковых должностей внутри одного подразделения рекомендуется использовать:

    CREATE UNIQUE INDEX positions_department_name_uq
        ON positions (
            department_id,
            LOWER(name)
        );

При этом одинаковое название должности может существовать в разных подразделениях.

Например:

    Аналитик
        -> Коммерческая аналитика

и:

    Аналитик
        -> Региональная аналитика

могут рассматриваться как разные должности.

В рамках MVP должности не удаляются физически.

Для исключения должности из новых назначений используется:

    is_active = FALSE

Деактивация должности:

- не удаляет запись;
- не очищает существующие назначения пользователей;
- запрещает назначение этой должности новым пользователям;
- сохраняет историческую согласованность данных.

Администратор может изменить подразделение должности.

Однако если должность уже назначена одному или нескольким пользователям, перенос должности в другое подразделение должен быть отклонён до переназначения таких пользователей.

Это предотвращает ситуацию, при которой изменение одной записи `Position` автоматически и неявно изменяет подразделение сразу нескольких пользователей.

# 5. Сущность User

Таблица:

    users

Назначение — хранение учётных записей и профилей пользователей системы.

| Поле | PostgreSQL | Ограничения | Назначение |
| --- | --- | --- | --- |
| id | BIGINT | PK, GENERATED | Идентификатор пользователя |
| name | VARCHAR(100) | NOT NULL | Имя пользователя |
| email | VARCHAR(255) | NOT NULL, UNIQUE | Уникальный email и логин |
| password_hash | VARCHAR(255) | NOT NULL | Хеш пароля |
| avatar_url | VARCHAR(2048) | NULL | URL фотографии профиля |
| role | VARCHAR(20) | NOT NULL | Роль пользователя |
| status | VARCHAR(20) | NOT NULL, DEFAULT 'ACTIVE' | Статус учётной записи |
| position_id | BIGINT | NULL, FK | Назначенная должность |
| blocked_at | TIMESTAMPTZ | NULL | Время блокировки |
| created_at | TIMESTAMPTZ | NOT NULL | Дата создания |
| updated_at | TIMESTAMPTZ | NOT NULL | Дата последнего изменения |

Допустимые значения:

    role

- `USER`;
- `ADMIN`.

Ограничение:

    CHECK (
        role IN (
            'USER',
            'ADMIN'
        )
    )

Допустимые значения:

    status

- `ACTIVE`;
- `BLOCKED`.

Ограничение:

    CHECK (
        status IN (
            'ACTIVE',
            'BLOCKED'
        )
    )

Для обеспечения согласованности статуса пользователя и времени блокировки используется:

    CHECK (
        (
            status = 'ACTIVE'
            AND blocked_at IS NULL
        )
        OR
        (
            status = 'BLOCKED'
            AND blocked_at IS NOT NULL
        )
    )

Внешний ключ:

    users.position_id
        -> positions.id

Правило удаления:

    ON DELETE RESTRICT

Поле:

    position_id

допускает `NULL`.

Это необходимо, поскольку новый пользователь может самостоятельно зарегистрироваться до того, как администратор назначит ему должность.

После регистрации пользователь получает:

    role = 'USER'

и:

    status = 'ACTIVE'

Должность назначается позднее администратором.

# 6. Связь пользователя с подразделением

Отдельное поле:

    department_id

в таблице:

    users

не используется.

Подразделение пользователя определяется через назначенную должность:

    users.position_id
        -> positions.department_id
        -> departments.id

Таким образом:

    User
        -> Position
        -> Department

Например:

    Пользователь
        position_id = 15

    Position 15
        name = Senior Developer
        department_id = 3

    Department 3
        name = Отдел разработки

Следовательно, подразделением пользователя является:

    Отдел разработки

Такой подход исключает состояние:

    department_id = Отдел маркетинга
    position_id = Senior Developer / Отдел разработки

которое могло бы возникнуть при независимом хранении обоих внешних ключей в таблице `users`.

---

# 7. Выбор подразделения и должности в интерфейсе

Несмотря на отсутствие:

    users.department_id

в пользовательском интерфейсе администратор работает с двумя полями:

    Подразделение

и:

    Должность

Подразделение используется как первый уровень выбора.

После выбора подразделения Frontend отображает только активные должности данного подразделения.

Например:

    Подразделение:
    Отдел разработки

    Должности:
    Junior Developer
    Middle Developer
    Senior Developer

После выбора должности Backend получает:

    position_id

и выполняет собственную проверку.

Backend должен проверить:

1. существование должности;
2. активность должности;
3. существование связанного подразделения;
4. активность подразделения;
5. принадлежность должности ожидаемому подразделению.

После успешной проверки в `users` сохраняется только:

    position_id

Подразделение определяется через `Position`.

Frontend-валидация не заменяет эту проверку.

# 8. Профиль пользователя

Пользователь может самостоятельно изменять:

- `name`;
- `email`;
- фотографию профиля.

Пользователь не может самостоятельно изменять:

- `role`;
- `status`;
- `position_id`;
- подразделение.

Эти данные изменяются только административными операциями.

Поле:

    avatar_url

содержит только URL изображения.

Например:

    https://storage.example.com/users/15/avatar.webp

Сам бинарный файл фотографии в PostgreSQL не хранится.

Production-поток:

    User
        -> Frontend
        -> Backend
        -> Object Storage
        -> URL
        -> PostgreSQL users.avatar_url

Секреты доступа к объектному хранилищу не хранятся в таблице `users`.

---

# 9. Блокировка пользователей

Для блокировки пользователя используется:

    status = 'BLOCKED'

и:

    blocked_at = <timestamp>

При разблокировке:

    status = 'ACTIVE'

и:

    blocked_at = NULL

Физическое удаление пользователя не является штатным механизмом ограничения доступа.

Пользователь со статусом:

    BLOCKED

не должен иметь возможность:

- выполнить авторизацию;
- использовать защищённые операции с ранее полученным JWT.

Актуальный статус пользователя проверяется Backend.

---

# 10. Ограничения администратора

Пользователь с ролью `ADMIN` может изменять:

- роль другого пользователя;
- статус другого пользователя;
- назначенную должность;
- организационные справочники.

Backend должен обеспечивать следующие бизнес-правила:

- администратор не может заблокировать самого себя;
- администратор не может самостоятельно изменить собственную роль `ADMIN` на `USER`;
- нельзя заблокировать последнего активного администратора;
- нельзя изменить роль последнего активного администратора на `USER`.

Ограничение последнего активного администратора невозможно полностью выразить простым `CHECK`.

Оно должно контролироваться транзакционной бизнес-логикой Backend.

При проверке рассматриваются пользователи:

    role = 'ADMIN'
    AND
    status = 'ACTIVE'

После административной операции в системе должен оставаться как минимум один активный администратор.

# 11. Сущность Product

Таблица:

    products

Представляет товар, для которого хранятся исторические продажи и формируются прогнозы.

| Поле | PostgreSQL | Ограничения | Назначение |
| --- | --- | --- | --- |
| id | BIGINT | PK, GENERATED | Идентификатор товара |
| sku | VARCHAR(64) | NOT NULL, UNIQUE | Уникальный код товара |
| name | VARCHAR(255) | NOT NULL | Наименование |
| category | VARCHAR(120) | NULL | Категория |
| created_at | TIMESTAMPTZ | NOT NULL | Дата создания |
| updated_at | TIMESTAMPTZ | NOT NULL | Дата изменения |

Поле:

    sku

используется при:

- поиске товара;
- сопоставлении строк CSV;
- идентификации товара во внешних данных.

Наименование товара не используется как технический идентификатор.

# 12. Сущность Sale

Таблица:

    sales

Представляет агрегированное количество проданных единиц конкретного товара за календарную дату.

Для текущей версии системы используется гранулярность:

**один товар — одна дата — одно агрегированное значение продаж.**

Это упрощает построение временного ряда.

| Поле | PostgreSQL | Ограничения | Назначение |
| --- | --- | --- | --- |
| id | BIGINT | PK, GENERATED | Идентификатор |
| product_id | BIGINT | NOT NULL, FK | Товар |
| sale_date | DATE | NOT NULL | Дата |
| quantity | INTEGER | NOT NULL | Количество проданных единиц |
| created_at | TIMESTAMPTZ | NOT NULL | Дата создания записи |

Внешний ключ:

    sales.product_id
        -> products.id

Правило удаления:

    ON DELETE RESTRICT

Количество должно удовлетворять:

    CHECK (
        quantity >= 0
    )

Комбинация:

    product_id
    sale_date

должна быть уникальной.

Ограничение:

    UNIQUE (
        product_id,
        sale_date
    )

Если при импорте CSV обнаруживается несколько строк для одного товара и одной даты, они должны быть обработаны в соответствии с правилами импорта до сохранения итогового значения.

# 13. Сущность Forecast

Таблица:

    forecasts

Представляет отдельный запуск прогнозирования.

| Поле | PostgreSQL | Ограничения | Назначение |
| --- | --- | --- | --- |
| id | BIGINT | PK, GENERATED | Идентификатор прогноза |
| user_id | BIGINT | NOT NULL, FK | Пользователь, инициировавший запуск |
| product_id | BIGINT | NOT NULL, FK | Прогнозируемый товар |
| forecast_horizon | INTEGER | NOT NULL | Горизонт прогнозирования |
| model_version | VARCHAR(100) | NOT NULL | Версия модели |
| status | VARCHAR(20) | NOT NULL | Состояние запуска |
| mae | NUMERIC(18,6) | NULL | MAE |
| rmse | NUMERIC(18,6) | NULL | RMSE |
| mape | NUMERIC(18,6) | NULL | MAPE |
| created_at | TIMESTAMPTZ | NOT NULL | Дата создания |
| started_at | TIMESTAMPTZ | NULL | Начало обработки |
| completed_at | TIMESTAMPTZ | NULL | Завершение |
| error_message | VARCHAR(1000) | NULL | Безопасное описание ошибки |

Внешние ключи:

    forecasts.user_id
        -> users.id

    forecasts.product_id
        -> products.id

Для обеих связей используется:

    ON DELETE RESTRICT

Допустимые значения:

    status

- `PENDING`;
- `PROCESSING`;
- `COMPLETED`;
- `FAILED`.

Ограничение:

    CHECK (
        status IN (
            'PENDING',
            'PROCESSING',
            'COMPLETED',
            'FAILED'
        )
    )

Горизонт прогнозирования должен быть положительным:

    CHECK (
        forecast_horizon > 0
    )

Показатели качества могут отсутствовать, если для соответствующего периода ещё невозможно выполнить сравнение с фактическими значениями.

# 14. Сущность ForecastValue

Таблица:

    forecast_values

Содержит отдельные прогнозируемые значения, относящиеся к одному запуску.

| Поле | PostgreSQL | Ограничения | Назначение |
| --- | --- | --- | --- |
| id | BIGINT | PK, GENERATED | Идентификатор |
| forecast_id | BIGINT | NOT NULL, FK | Прогноз |
| forecast_date | DATE | NOT NULL | Дата прогнозируемого значения |
| predicted_quantity | NUMERIC(18,4) | NOT NULL | Прогнозируемый спрос |

Внешний ключ:

    forecast_values.forecast_id
        -> forecasts.id

Используется:

    ON DELETE CASCADE

Это оправдано тем, что `ForecastValue` не имеет самостоятельного смысла без родительского `Forecast`.

Для одного прогноза должна существовать только одна запись на конкретную дату:

    UNIQUE (
        forecast_id,
        forecast_date
    )

Прогнозируемое количество не должно быть отрицательным:

    CHECK (
        predicted_quantity >= 0
    )

---

# 15. Почему фактические значения не дублируются в ForecastValue

Фактический спрос уже хранится в таблице:

    sales

Поэтому поле:

    actual_quantity

в:

    forecast_values

не добавляется.

Это предотвращает хранение одного фактического значения одновременно:

- в `sales`;
- в `forecast_values`.

При необходимости сравнения прогнозного и фактического значения Backend сопоставляет:

- `forecast_values.forecast_date`;
- `sales.sale_date`;
- товар, связанный с Forecast.

Таким образом устраняется избыточность данных.

# 16. Связи сущностей

Основные отношения:

    Department 1 ----- * Position

    Position 1 ------- * User
    User -> Position является необязательной связью

    User 1 ----------- * Forecast

    Product 1 -------- * Sale

    Product 1 -------- * Forecast

    Forecast 1 ------- * ForecastValue

## 16.1. Department → Position

Одно подразделение может содержать множество должностей.

Каждая должность принадлежит ровно одному подразделению.

## 16.2. Position → User

Одна должность может быть назначена множеству пользователей.

У одного пользователя:

- может отсутствовать должность;
- либо может быть назначена одна должность.

## 16.3. User → Forecast

Один пользователь может создать множество прогнозов.

Каждый прогноз связан с одним пользователем.

## 16.4. Product → Sale

Один товар может иметь множество исторических значений продаж.

Каждая запись Sale относится к одному товару.

## 16.5. Product → Forecast

Для одного товара может быть сформировано множество прогнозов.

Каждый Forecast строится для одного товара.

## 16.6. Forecast → ForecastValue

Один Forecast содержит множество прогнозируемых значений.

Каждый ForecastValue относится к одному Forecast.

            | *

    |      User      |
    +----------------+

    | email          |
    | avatar_url     |
    | role           |
    | status         |
    | blocked_at     |
    +-------+--------+
            |
            | 1

            | *
    +-------v--------+

# 18. Нормализация

Структура базы данных приводится к третьей нормальной форме.

## 18.1. Первая нормальная форма

Все атрибуты являются атомарными.

В одном поле не хранятся:

- списки подразделений;
- списки должностей;
- списки товаров;
- списки продаж;
- списки прогнозируемых дат.

Следовательно, требования первой нормальной формы выполняются.

## 18.2. Вторая нормальная форма

Каждая таблица имеет однозначный первичный ключ.

Неключевые атрибуты зависят от полного первичного ключа.

Данные связанных сущностей не копируются в дочерние таблицы текстом, а определяются через внешние ключи.

Например:

    users.position_id

содержит ссылку на должность, а не название должности.

Следовательно, частичные функциональные зависимости отсутствуют.

## 18.3. Третья нормальная форма

Неключевые атрибуты не должны зависеть друг от друга транзитивно.

Поэтому:

- название подразделения не хранится в `users`;
- название должности не хранится в `users`;
- `department_id` не хранится в `users`;
- подразделение определяется через `position_id`;
- данные товара не копируются в `sales`;
- Forecast не хранит email пользователя;
- Forecast не хранит название или SKU товара;
- ForecastValue не дублирует характеристики Forecast;
- ForecastValue не дублирует фактические продажи.

Организационная принадлежность определяется через:

    User
        -> Position
        -> Department

Таким образом транзитивное дублирование устраняется.

Модель соответствует третьей нормальной форме.

# 21. Уникальные ограничения

Используются следующие ограничения:

    users.email

    products.sku

    sales(product_id, sale_date)

    forecast_values(forecast_id, forecast_date)

Для организационной структуры дополнительно рекомендуется:

    CREATE UNIQUE INDEX departments_name_uq
        ON departments (LOWER(name));

и:

    CREATE UNIQUE INDEX positions_department_name_uq
        ON positions (
            department_id,
            LOWER(name)
        );

Первый индекс предотвращает создание одинаковых подразделений без учёта регистра.

Второй предотвращает создание одинаковых должностей внутри одного подразделения.

# 22. CHECK-ограничения

Необходимо определить как минимум:

    users.role IN (
        'USER',
        'ADMIN'
    )

    users.status IN (
        'ACTIVE',
        'BLOCKED'
    )

    (
        (
            users.status = 'ACTIVE'
            AND users.blocked_at IS NULL
        )
        OR
        (
            users.status = 'BLOCKED'
            AND users.blocked_at IS NOT NULL
        )
    )

    sales.quantity >= 0

    forecasts.forecast_horizon > 0

    forecasts.status IN (
        'PENDING',
        'PROCESSING',
        'COMPLETED',
        'FAILED'
    )

    forecast_values.predicted_quantity >= 0

Некоторые межтабличные бизнес-правила невозможно корректно выразить простым `CHECK`.

К ним относятся:

- запрет назначения неактивной должности;
- запрет назначения должности неактивного подразделения;
- защита последнего активного администратора;
- запрет переноса назначенной должности в другое подразделение.

Эти правила проверяются Backend в рамках транзакционных операций.

# 23. Индексы

PostgreSQL автоматически создаёт индексы для:

- `PRIMARY KEY`;
- обычных `UNIQUE`-ограничений.

Дополнительно создаются индексы под основные сценарии чтения.

## 23.1. Должности подразделения

    CREATE INDEX positions_department_active_idx
        ON positions (
            department_id,
            is_active
        );

Используется для:

- получения должностей подразделения;
- формирования dropdown должностей;
- получения только активных вариантов.

## 23.2. Пользователи по должности

    CREATE INDEX users_position_idx
        ON users (
            position_id
        );

Используется для:

- поиска пользователей конкретной должности;
- проверки существующих назначений перед переносом должности.

## 23.3. Пользователи по роли и статусу

    CREATE INDEX users_role_status_idx
        ON users (
            role,
            status
        );

Используется при проверке количества активных администраторов.

## 23.4. История продаж товара

    CREATE INDEX sales_product_date_idx
        ON sales (
            product_id,
            sale_date
        );

Используется при:

- просмотре продаж товара;
- фильтрации по диапазону;
- получении временного ряда для прогнозирования.

## 23.5. История прогнозов пользователя

    CREATE INDEX forecasts_user_created_idx
        ON forecasts (
            user_id,
            created_at DESC
        );

Используется для просмотра истории прогнозов пользователя.

## 23.6. Прогнозы товара

    CREATE INDEX forecasts_product_created_idx
        ON forecasts (
            product_id,
            created_at DESC
        );

Используется для:

- фильтрации истории;
- анализа прогнозов конкретного товара.

## 23.7. Значения прогноза

Ограничение:

    UNIQUE (
        forecast_id,
        forecast_date
    )

уже создаёт соответствующий индекс.

Отдельный индекс на те же поля не требуется.

## 23.8. Email и SKU

Отдельные индексы не требуются, поскольку:

    UNIQUE users.email

и:

    UNIQUE products.sku

уже создают необходимые уникальные индексы.

---

# 24. Необязательные индексы

Не следует создавать индексы на каждое поле заранее.

Например, индекс:

    products.category

необходим только в случае, если фильтрация по категории станет частым подтверждённым сценарием.

Индексы:

- ускоряют чтение;
- увеличивают затраты на запись;
- занимают место.

Поэтому дополнительные индексы должны добавляться на основании фактических запросов.

# 25. Правила удаления и деактивации

## 25.1. Department

Физическое удаление подразделения не является штатной операцией MVP.

Используется:

    is_active = FALSE

Деактивация подразделения:

- не удаляет его должности;
- не удаляет пользователей;
- не изменяет существующие назначения;
- запрещает новые назначения через это подразделение.

## 25.2. Position

Физическое удаление должности не является штатной операцией MVP.

Используется:

    is_active = FALSE

Деактивация:

- не очищает `users.position_id`;
- сохраняет существующие назначения;
- запрещает новые назначения.

## 25.3. User

Физическое удаление пользователя не является штатным механизмом административного управления.

Для ограничения доступа используется:

    status = 'BLOCKED'

Если пользователь связан с Forecast, физическое удаление ограничивается ссылочной целостностью.

## 25.4. Product

Удаление товара запрещается, если существуют связанные:

- `Sale`;
- `Forecast`.

Это предотвращает потерю истории.

## 25.5. Sale

Продажи могут изменяться или удаляться только административным сценарием, если такой функционал будет предусмотрен.

Массовое случайное удаление через каскад Product запрещено.

## 25.6. Forecast

При удалении Forecast связанные ForecastValue удаляются каскадно.

# 26. Временные данные

Для системных временных отметок используется:

    TIMESTAMPTZ

Это относится к:

- `created_at`;
- `updated_at`;
- `blocked_at`;
- `started_at`;
- `completed_at`.

Тип `TIMESTAMPTZ` позволяет однозначно хранить момент времени независимо от часового пояса приложения.

Для предметных календарных дат используется:

    DATE

Это относится к:

- `sale_date`;
- `forecast_date`.

# 27. Числовые типы

Для фактического количества продаж используется:

    INTEGER

поскольку в текущей предметной модели количество проданных единиц является целым числом.

Для результата модели используется:

    NUMERIC(18,4)

поскольку нейросетевая модель может возвращать дробное прогнозируемое значение.

Метрики используют:

    NUMERIC(18,6)

для сохранения необходимой точности.

# 28. Модель хранения метрик

В текущей версии:

    mae
    rmse
    mape

хранятся непосредственно в:

    forecasts

Это не нарушает третью нормальную форму, поскольку каждое значение функционально зависит непосредственно от конкретного Forecast.

Создание отдельной таблицы метрик для трёх фиксированных показателей в MVP не требуется.

Если в дальнейшем набор метрик станет динамическим, модель может быть расширена отдельной сущностью.

# 29. Версия ML-модели

Поле:

    forecasts.model_version

сохраняет версию модели, фактически использованную для получения результата.

Например:

    lstm-1.0.0

Это необходимо для:

- воспроизводимости;
- анализа предыдущих прогнозов;
- сравнения результатов разных версий модели.

Отдельная таблица моделей на текущем этапе не вводится.

# 34. Итоговая модель организационной структуры

Основной принцип организационной модели:

    Department
        -> Position
        -> User

Должность обязательно принадлежит подразделению.

Пользователь может не иметь должности сразу после регистрации.

После назначения должности подразделение пользователя автоматически определяется через эту должность.

Пример:

    departments

    id = 1
    name = "Отдел разработки"

            |
            v

    positions

    id = 5
    department_id = 1
    name = "Senior Developer"

            |
            v

    users

    id = 10
    position_id = 5
    name = "Иван Иванов"

Из этих данных однозначно следует:

    Иван Иванов
        -> Senior Developer
        -> Отдел разработки

Отдельно сохранять:

    users.department_id

не требуется.

# 35. Результат

Сформирована нормализованная реляционная модель PostgreSQL для программного средства прогнозирования потребительского спроса.

Модель:

- соответствует функциональным требованиям;
- соответствует пользовательским сценариям;
- содержит сущности организационной структуры;
- обеспечивает обязательную связь должности с подразделением;
- исключает противоречие между должностью и подразделением пользователя;
- поддерживает административное управление пользователями;
- поддерживает статусы `ACTIVE` и `BLOCKED`;
- поддерживает роли `USER` и `ADMIN`;
- хранит только URL фотографии профиля;
- не хранит бинарные изображения в PostgreSQL;
- приведена к третьей нормальной форме;
- определяет первичные и внешние ключи;
- устанавливает ограничения целостности;
- определяет необходимые индексы;
- обеспечивает хранение исторических продаж;
- обеспечивает хранение результатов прогнозирования;
- поддерживает последующую реализацию Backend;
- поддерживает интеграцию с ML-сервисом и объектным хранилищем.
