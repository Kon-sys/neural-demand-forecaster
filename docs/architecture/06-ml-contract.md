# Контракт взаимодействия Backend и ML-компонента

## 1. Назначение документа

Настоящий документ определяет контракт взаимодействия между основной серверной частью программного средства и компонентом машинного обучения.

Контракт должен изолировать Backend от внутренней реализации модели и позволять изменять модель прогнозирования без значительных изменений прикладной логики.

## 2. Принцип взаимодействия

Backend не должен обращаться непосредственно к конкретной реализации нейросетевой модели.

Взаимодействие выполняется через абстракцию Forecasting Service и её техническую реализацию — Forecasting Adapter.

Общая схема:

    Forecast Service
          |
          v
    Forecasting Adapter
          |
          v
    ML Component
          |
          v
    Trained Model

## 3. Ответственность Backend

Backend отвечает за:

- обработку пользовательского запроса;
- проверку существования Dataset;
- проверку выбранного объекта;
- проверку горизонта;
- получение исходных данных;
- формирование контекста запуска;
- вызов Forecasting Adapter;
- сохранение результата;
- обработку технических ошибок;
- предоставление ответа клиенту.

## 4. Ответственность ML-компонента

ML-компонент отвечает за:

- загрузку нужной версии модели;
- применение преобразований, являющихся частью ML-pipeline;
- формирование входного тензора;
- выполнение inference;
- обратное преобразование результата при необходимости;
- возврат прогнозируемых значений;
- возврат версии модели;
- обнаружение ошибок, связанных с ML-процессом.

## 5. Граница предварительной обработки

Необходимо разделять:

### Прикладную подготовку данных

Может выполняться Backend или специализированным Data Processing модулем:

- чтение данных;
- проверка структуры;
- фильтрация;
- выбор товара;
- сортировка;
- базовая очистка.

### ML-преобразования

Должны выполняться согласованно с обучением модели:

- масштабирование;
- кодирование признаков;
- формирование окон;
- преобразование в тензоры;
- обратное масштабирование результата.

Преобразования, параметры которых были получены во время обучения модели, должны храниться вместе с ML-артефактами и применяться ML-компонентом.

Это снижает риск различий между training и inference pipeline.

## 6. Логический запрос прогнозирования

Backend должен передать данные, достаточные для выполнения inference.

Пример логической структуры:

    {
      "requestId": "req_001",
      "modelVersion": "1.0.0",
      "forecastHorizon": 14,
      "series": [
        {
          "date": "2026-08-01",
          "value": 120.0
        },
        {
          "date": "2026-08-02",
          "value": 124.0
        }
      ],
      "features": {
      }
    }

Точная структура `features` зависит от окончательно выбранной модели.

## 7. Логический успешный ответ

Пример:

    {
      "requestId": "req_001",
      "modelName": "demand-forecast-model",
      "modelVersion": "1.0.0",
      "predictions": [
        {
          "date": "2026-09-01",
          "value": 128.4
        },
        {
          "date": "2026-09-02",
          "value": 130.1
        }
      ]
    }

Backend не должен зависеть от внутренних тензоров, слоёв нейросети или других деталей реализации модели.

## 8. Ошибки ML-компонента

ML-компонент должен возвращать технически определимые ошибки.

Основные категории:

    INVALID_INPUT
    INSUFFICIENT_HISTORY
    MODEL_NOT_FOUND
    MODEL_LOADING_ERROR
    PREPROCESSING_ERROR
    INFERENCE_ERROR
    INVALID_OUTPUT
    INTERNAL_ERROR

Пример логического ответа:

    {
      "code": "INSUFFICIENT_HISTORY",
      "message": "Недостаточно исторических данных для выполнения прогнозирования"
    }

Backend должен преобразовывать внутренние ошибки ML в безопасные прикладные ошибки для клиента.

## 9. Timeout

Вызов ML-компонента должен иметь ограничение времени выполнения.

Backend не должен бесконечно ожидать ответ модели.

Конкретное значение timeout определяется экспериментально после реализации модели и измерения реального времени inference.

## 10. Retry

Автоматический повтор допустим только для ошибок, имеющих временный технический характер.

Например:

- временная недоступность ML-сервиса;
- кратковременная ошибка соединения.

Retry не должен применяться к:

- некорректным данным;
- недостаточной истории;
- отсутствующей модели;
- ошибкам preprocessing.

Количество повторов должно быть ограничено.

## 11. Идемпотентность

Повторная техническая отправка одного и того же ML-запроса не должна автоматически приводить к созданию нескольких Forecast в базе данных.

Созданием и идентификацией Forecast управляет Backend.

`requestId` может использоваться для корреляции запросов между компонентами.

## 12. Версионирование модели

ML-компонент должен возвращать фактически использованную версию модели.

Backend сохраняет её вместе с Forecast.

Версия должна однозначно определять ML-артефакт, использованный при формировании результата.

## 13. Версионирование preprocessing

Если preprocessing является частью ML-pipeline, рекомендуется хранить его версию вместе с версией модели.

Например:

    modelVersion: 1.0.0
    preprocessingVersion: 1.0.0

Это необходимо для воспроизводимости результатов.

## 14. Health Check

Если ML-компонент реализован отдельным процессом или сервисом, он должен предоставлять технический способ проверки доступности.

Логический endpoint:

    GET /health

Пример:

    {
      "status": "UP",
      "modelLoaded": true,
      "modelVersion": "1.0.0"
    }

Health Check используется для технической диагностики и не является пользовательской функцией.

## 15. Способ физической интеграции

Контракт не должен жёстко привязывать Backend к конкретному механизму интеграции.

Возможные варианты:

- отдельный HTTP-сервис на Python;
- локальный Python-процесс;
- другой технический адаптер.

Для учебного проекта предпочтительным вариантом является отдельный лёгкий ML-сервис с HTTP API, если это не создаёт неоправданную сложность.

Окончательное решение принимается при выборе технологического стека.

## 16. Требования к логированию

Backend должен регистрировать:

- идентификатор Forecast;
- requestId;
- начало вызова ML;
- завершение вызова;
- продолжительность;
- категорию ошибки при неуспешном результате.

Не следует регистрировать полный набор пользовательских данных без необходимости.

## 17. Результат

Определённый контракт отделяет прикладную серверную логику от внутренней реализации модели прогнозирования.

Backend взаимодействует с абстракцией Forecasting Service, а Forecasting Adapter отвечает за техническое взаимодействие с ML-компонентом.

Такой подход позволяет независимо изменять модель, механизм её запуска и внутренний ML-pipeline при сохранении стабильного контракта основной системы.
