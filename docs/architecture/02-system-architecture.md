# Архитектура программного средства

## 1. Назначение документа

Документ определяет архитектуру программного средства прогнозирования потребительского спроса, ответственность основных компонентов, способы их взаимодействия и движение данных между ними.

Архитектура сформирована на основании:

- границ MVP;
- функциональных и нефункциональных требований;
- пользовательских сценариев;
- бизнес-процесса TO-BE.

## 2. Архитектурный подход

Для программного средства используется клиент-серверная архитектура с выделенным ML-компонентом.

Система состоит из пяти основных компонентов:

1. Frontend;
2. Backend;
3. ML-сервис;
4. PostgreSQL;
5. внешнее объектное хранилище фотографий профиля.

Компоненты разделены по ответственности и взаимодействуют через явно определённые интерфейсы.

ML-сервис выделяется отдельно от Backend из-за использования отдельного технологического стека и необходимости изолировать особенности машинного обучения от основной бизнес-логики.

Система не рассматривается как полноценная микросервисная архитектура. Разделение Backend и ML-сервиса является техническим решением, соответствующим задачам проекта.

## 3. Общая схема

Архитектура системы имеет следующий вид:

    Пользователь / Администратор
                |
                | HTTPS
                v
        +------------------+
        |     Frontend     |
        |   React / Vite   |
        +--------+---------+
                 |
                 | REST API / JSON
                 | multipart/form-data
                 v
        +------------------+
        |     Backend      |
        |   Spring Boot    |
        +---+----------+---+
            |          |
       JDBC |          | HTTP / JSON
            v          v
    +-------------+  +------------------+
    | PostgreSQL  |  |    ML-сервис     |
    +-------------+  |     FastAPI      |
            ^        +------------------+
            |
            | URL фотографии
            |
    +----------------------+
    | Объектное хранилище  |
    | фотографий профиля   |
    +----------------------+
            ^
            |
            | upload/delete
            |
          Backend

Frontend не взаимодействует напрямую с PostgreSQL и ML-сервисом.

Привилегированный доступ к объектному хранилищу выполняется только через Backend.

Backend является центральным компонентом, координирующим прикладные сценарии.

## 4. Frontend

Frontend представляет пользовательский интерфейс системы.

Основные обязанности Frontend:

- отображение страниц приложения;
- маршрутизация;
- регистрация пользователя;
- авторизация;
- хранение состояния пользовательской сессии;
- работа с JWT;
- отображение товаров;
- отображение истории продаж;
- загрузка CSV;
- настройка параметров прогнозирования;
- запуск прогноза;
- отображение состояния выполнения операций;
- визуализация исторических и прогнозируемых значений;
- отображение MAE, RMSE и MAPE;
- просмотр истории прогнозов;
- просмотр и изменение разрешённых полей профиля;
- загрузка, замена и удаление фотографии профиля;
- отображение назначенных подразделения, должности, роли и статуса;
- административное управление пользователями;
- административное управление подразделениями и должностями;
- фильтрация должностей по выбранному подразделению;
- отображение ошибок API.

Frontend не должен содержать критическую бизнес-логику.

Клиентская проверка данных используется для улучшения пользовательского опыта, но не заменяет серверную валидацию.

## 5. Backend

Backend является центральным прикладным компонентом системы.

Он реализуется как Spring Boot приложение.

Основные обязанности Backend:

- регистрация пользователей;
- авторизация;
- выдача и проверка JWT;
- проверка ролей и актуального статуса учётной записи;
- управление профилями пользователей;
- административное управление пользователями;
- защита собственной учётной записи администратора и последнего активного администратора;
- управление подразделениями и должностями;
- проверка принадлежности должности подразделению;
- управление фотографиями профиля через объектное хранилище;
- управление товарами;
- хранение и получение продаж;
- импорт CSV;
- валидация входных данных;
- взаимодействие с PostgreSQL;
- получение исторических данных для прогнозирования;
- взаимодействие с ML-сервисом;
- сохранение прогнозов;
- предоставление истории прогнозирования;
- централизованная обработка ошибок;
- журналирование.

Backend является единственной точкой доступа Frontend к прикладным данным системы.

## 6. Логические модули Backend

Backend должен быть разделён по предметным областям.

Рекомендуемая логическая структура:

    auth
    user
    organization
    storage
    product
    sale
    import
    forecast
    ml
    common

### auth

Отвечает за:

- регистрацию;
- авторизацию;
- JWT;
- проверку безопасности.

### user

Отвечает за:

- модель пользователя;
- просмотр и изменение разрешённых полей собственного профиля;
- административный список пользователей;
- изменение роли и статуса;
- назначение должности;
- защиту собственной учётной записи администратора;
- защиту последнего активного администратора.

### organization

Отвечает за:

- подразделения;
- должности;
- обязательную связь каждой должности с одним подразделением;
- активацию и деактивацию справочников;
- проверку допустимости должности при назначении пользователю.

### storage

Содержит адаптер взаимодействия Backend с объектным хранилищем фотографий.

Отвечает за:

- загрузку фотографии;
- замену фотографии;
- удаление объекта;
- получение URL сохранённого изображения;
- изоляцию Frontend и доменной логики от конкретного поставщика хранилища.

### product

Отвечает за:

- создание товаров;
- получение товаров;
- изменение;
- удаление;
- поиск.

### sale

Отвечает за:

- хранение продаж;
- получение истории;
- фильтрацию.

### import

Отвечает за:

- загрузку CSV;
- чтение файла;
- валидацию;
- обработку строк;
- формирование отчёта импорта.

### forecast

Отвечает за:

- запуск прогнозирования;
- получение исторических данных;
- вызов ML-компонента;
- сохранение Forecast;
- сохранение ForecastValue;
- получение истории прогнозов.

### ml

Содержит адаптер взаимодействия Backend с ML-сервисом.

Основная бизнес-логика не должна зависеть непосредственно от FastAPI или внутреннего устройства Python-кода.

### common

Содержит общую инфраструктуру:

- обработку ошибок;
- конфигурацию;
- журналирование;
- общие DTO;
- вспомогательные компоненты.

## 7. PostgreSQL

PostgreSQL используется как основное долговременное хранилище прикладных данных.

В базе должны храниться как минимум:

- пользователи;
- подразделения;
- должности;
- URL фотографий профиля;
- товары;
- продажи;
- прогнозы;
- отдельные значения прогнозов.

Конкретная нормализованная схема определяется в `KP-12`.

Backend является единственным прикладным компонентом, который непосредственно работает с PostgreSQL.

Frontend и ML-сервис не должны обращаться к базе данных напрямую.

## 8. Объектное хранилище фотографий

Бинарные файлы фотографий профиля хранятся отдельно от PostgreSQL.

Backend взаимодействует с внешним объектным хранилищем через адаптер модуля `storage`.

Основной поток:

    Frontend
       |
       | multipart/form-data
       v
    Backend
       |
       | validation
       v
    Object Storage
       |
       | object URL
       v
    Backend
       |
       | save avatar_url
       v
    PostgreSQL

В PostgreSQL хранится только URL фотографии.

Frontend не получает секреты хранилища и не выполняет привилегированные операции напрямую.

Конкретный поставщик хранилища не должен влиять на пользовательскую и доменную логику Backend.

## 9. ML-сервис

ML-сервис реализуется отдельно с использованием FastAPI.

Он предназначен для применения модели прогнозирования.

Основные обязанности:

- предоставление `/health`;
- предоставление `/predict`;
- загрузка обученной модели;
- загрузка необходимых preprocessing-артефактов;
- подготовка входной последовательности;
- выполнение inference;
- обратное преобразование результата при необходимости;
- возврат прогнозных значений;
- возврат версии модели;
- контролируемая обработка ML-ошибок;
- журналирование.

ML-сервис не отвечает за:

- пользователей;
- роли;
- товары;
- долговременное хранение продаж;
- долговременное хранение прогнозов;
- принятие решений о доступе.

Эти функции относятся к Backend.

## 10. Взаимодействие Frontend и Backend

Взаимодействие выполняется посредством REST API.

Основным форматом структурированных данных является JSON.

Для передачи CSV и фотографий профиля используется `multipart/form-data`.

Frontend передаёт JWT в защищённых запросах.

Общий поток:

    Frontend
       |
       | HTTP request
       v
    Backend
       |
       | validation
       | business logic
       v
    PostgreSQL / ML-service
       |
       v
    Backend
       |
       | HTTP response
       v
    Frontend

## 11. Взаимодействие Backend и ML-сервиса

Backend взаимодействует с ML-сервисом через HTTP REST API.

ML-сервис предоставляет:

    GET /health
    POST /predict

Frontend не должен вызывать эти endpoint напрямую.

Последовательность:

    ForecastService
         |
         v
    MlClient
         |
         v
    FastAPI /predict
         |
         v
    ML pipeline
         |
         v
    PredictionResponse

Backend должен использовать timeout при вызове ML-сервиса.

Недоступность ML-сервиса должна обрабатываться как контролируемая прикладная ошибка.

## 12. Поток регистрации

Основной поток регистрации:

    Пользователь
        |
        v
    Frontend
        |
        | registration request
        v
    Backend
        |
        | validation
        | password hashing
        v
    PostgreSQL
        |
        v
    Backend
        |
        v
    Frontend

Пароль в открытом виде не сохраняется.

Новый пользователь получает роль `USER` и статус `ACTIVE`.

Должность у нового пользователя может отсутствовать до назначения администратором.

## 13. Поток авторизации

    Пользователь
        |
        v
    Frontend
        |
        | credentials
        v
    Backend
        |
        | user lookup
        | password verification
        | account status check
        v
    PostgreSQL
        |
        v
    Backend
        |
        | JWT
        v
    Frontend

JWT используется для последующих защищённых запросов.

Пользователь со статусом `BLOCKED` не должен получать новую авторизованную сессию. Backend также должен учитывать актуальный статус учётной записи при выполнении защищённых запросов, чтобы ранее выданный JWT не обходил административную блокировку.

## 14. Поток работы с профилем

Пользователь получает собственный профиль через Backend.

Изменяемыми пользователем являются только:

- имя;
- email;
- фотография профиля.

Роль, статус, должность и подразделение доступны пользователю только для просмотра.

Подразделение определяется через назначенную должность.

## 15. Поток загрузки фотографии профиля

    Пользователь
        |
        | image file
        v
    Frontend
        |
        | multipart/form-data
        v
    Backend
        |
        +--> проверка MIME-типа и размера
        |
        v
    Object Storage
        |
        | URL
        v
    Backend
        |
        | save avatar_url
        v
    PostgreSQL

При замене фотографии Backend сначала должен успешно сохранить новый объект и получить его URL. После этого обновляется ссылка пользователя. Удаление старого объекта выполняется после успешного обновления данных профиля.

## 16. Поток административного управления пользователем

Администратор может изменять:

- роль;
- статус;
- назначенную должность.

В интерфейсе сначала выбирается подразделение. Затем Frontend отображает только активные должности данного подразделения.

Backend независимо проверяет, что выбранная должность:

- существует;
- активна;
- относится к активному подразделению;
- соответствует выбранному в интерфейсе подразделению.

Система не позволяет администратору заблокировать или понизить самого себя, а также оставить систему без активного администратора.

## 17. Поток управления организационной структурой

Администратор управляет подразделениями и должностями.

Каждая должность обязательно содержит ссылку на одно подразделение.

Деактивация подразделения или должности не удаляет существующие пользовательские назначения, но запрещает новые назначения деактивированных значений.

Изменение подразделения должности, уже назначенной пользователям, должно быть отклонено до переназначения этих пользователей, чтобы их организационная принадлежность не изменялась неявно.

## 18. Поток импорта CSV

    ADMIN
      |
      v
    Frontend
      |
      | CSV
      v
    Backend
      |
      +--> file validation
      |
      +--> structure validation
      |
      +--> row validation
      |
      +--> duplicate handling
      |
      v
    PostgreSQL
      |
      v
    Import Result
      |
      v
    Frontend

ML-сервис в этом сценарии не участвует.

## 19. Поток прогнозирования

Пользователь выбирает товар и горизонт прогнозирования.

Frontend передаёт запрос Backend.

Backend:

1. проверяет JWT;
2. проверяет параметры;
3. проверяет существование товара;
4. получает продажи товара из PostgreSQL;
5. проверяет достаточность истории;
6. формирует запрос ML-сервису;
7. вызывает `/predict`;
8. получает прогноз;
9. сохраняет Forecast;
10. сохраняет ForecastValue;
11. возвращает результат Frontend.

Логически:

    Frontend
       |
       v
    Backend
       |
       +------> PostgreSQL
       |         получить продажи
       |
       v
    ML-service
       |
       v
    Backend
       |
       +------> PostgreSQL
       |         сохранить Forecast
       |
       v
    Frontend

## 20. Поток просмотра истории прогнозов

    Frontend
       |
       | GET forecasts
       v
    Backend
       |
       v
    PostgreSQL
       |
       v
    Backend
       |
       v
    Frontend

Повторный просмотр сохранённого прогноза не должен требовать нового обращения к ML-сервису.

## 21. Обработка ошибок

Backend должен быть центральной точкой преобразования ошибок в единый формат API.

Категории ошибок:

- ошибка валидации;
- ошибка авторизации;
- отсутствие прав;
- ресурс не найден;
- конфликт данных;
- ошибка CSV;
- ошибка загрузки фотографии;
- недоступность объектного хранилища;
- заблокированная учётная запись;
- недопустимое изменение последнего активного администратора;
- конфликт должности и подразделения;
- недостаточно исторических данных;
- ML-сервис недоступен;
- ошибка ML inference;
- внутренняя ошибка.

Frontend получает безопасное описание ошибки.

Внутренний stack trace пользователю не передаётся.

## 22. Безопасность взаимодействия

Для системы применяются следующие архитектурные правила:

- пароль хранится только в хешированном виде;
- защищённые Backend endpoint требуют JWT;
- права `USER` и `ADMIN` проверяются на Backend;
- актуальный статус учётной записи проверяется на Backend;
- пользователь не может изменять через self-service API роль, статус и организационные атрибуты;
- административные операции с пользователями и организационной структурой доступны только `ADMIN`;
- Backend проверяет связь должности с подразделением независимо от Frontend;
- Frontend не считается доверенной стороной;
- секреты не хранятся в исходном коде;
- секреты объектного хранилища доступны только серверной части;
- Frontend не имеет прямого доступа к PostgreSQL;
- Frontend не вызывает ML-сервис напрямую;
- при внешнем развёртывании используется HTTPS.

## 23. Отказ ML-сервиса

Отказ ML-сервиса не должен делать недоступными остальные функции приложения.

При недоступности ML-сервиса пользователь по-прежнему должен иметь возможность:

- авторизоваться;
- просматривать товары;
- просматривать продажи;
- просматривать ранее сохранённые прогнозы;
- работать с профилем;
- выполнять административные операции, не связанные с ML-сервисом, при наличии соответствующих прав.

Недоступной становится только операция формирования нового прогноза.

## 24. Масштабирование архитектуры

Для текущей версии не требуется сложная распределённая инфраструктура.

В дальнейшем архитектура позволяет независимо:

- изменять Frontend;
- расширять Backend;
- заменять ML-модель;
- добавлять новые модели;
- изменять физическое размещение компонентов;
- расширять API.

## 25. Обоснование архитектуры

Выбранная архитектура соответствует задачам проекта по следующим причинам.

### Разделение ответственности

Каждый компонент отвечает за отдельную область.

### Изоляция ML

Python/ML-часть не смешивается с Java Backend.

### Централизованный Backend

Авторизация, права доступа и бизнес-правила контролируются одним компонентом.

### Централизованное хранение

PostgreSQL обеспечивает целостное хранение прикладных данных.

### Тестируемость

Backend и ML-сервис могут тестироваться независимо.

### Расширяемость

ML-модель можно заменить без полной переработки Frontend и Backend.

### Соответствие масштабу проекта

Архитектура не вводит необоснованно сложные инфраструктурные компоненты.
