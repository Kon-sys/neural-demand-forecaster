# Архитектура компонентов программного средства

## 1. Назначение документа

Настоящий документ определяет логическую архитектуру программного средства прогнозирования потребительского спроса и ответственность его основных компонентов.

Архитектура формируется на основании ранее определённых функциональных и нефункциональных требований.

## 2. Архитектурный подход

Для программного средства предлагается модульная клиент-серверная архитектура с отдельным компонентом прогнозирования.

Система разделяется на следующие основные уровни:

1. клиентский уровень;
2. серверный прикладной уровень;
3. уровень хранения данных;
4. компонент машинного обучения.

Такое разделение обеспечивает:

- слабую связанность компонентов;
- возможность независимого развития пользовательского интерфейса и ML-части;
- тестируемость бизнес-логики;
- возможность замены модели;
- централизованный контроль операций с данными.

## 4. Клиентское приложение

### 4.1. Ответственность

Клиентское приложение отвечает за взаимодействие пользователя с системой.

Основные функции:

- загрузка файла;
- отображение результатов проверки данных;
- настройка параметров прогнозирования;
- запуск прогнозирования;
- отображение состояния длительных операций;
- визуализация исторических и прогнозируемых значений;
- отображение метрик;
- просмотр истории прогнозов.

### 4.2. Ограничения

Клиентская часть не должна:

- выполнять нейросетевое прогнозирование;
- содержать основную бизнес-логику;
- обращаться напрямую к хранилищу;
- обращаться напрямую к ML-модели.

Все значимые операции выполняются через серверный API.

## 5. Backend API

Backend является центральным координирующим компонентом системы.

Он отвечает за:

- обработку запросов клиента;
- валидацию входных параметров;
- координацию пользовательских сценариев;
- работу с наборами данных;
- запуск предварительной обработки;
- взаимодействие с ML-компонентом;
- сохранение результатов;
- получение истории прогнозирования;
- централизованную обработку ошибок.

Backend не должен содержать детали реализации пользовательского интерфейса или внутренней архитектуры нейросетевой модели.

## 6. Модуль обработки данных

Модуль обработки данных отвечает за подготовку исходных данных к прогнозированию.

Основные функции:

- проверка структуры;
- проверка типов;
- поиск пропущенных значений;
- обработка дубликатов;
- сортировка по времени;
- агрегирование;
- формирование дополнительных признаков;
- масштабирование;
- формирование входных последовательностей.

Преобразования должны выполняться воспроизводимым способом.

Если определённые операции являются частью непосредственно ML-pipeline, их реализация может располагаться внутри ML-компонента. При этом между серверной частью и ML-компонентом должен существовать однозначно определённый контракт передачи данных.

## 7. Forecasting Adapter

Для взаимодействия основной серверной части с ML-компонентом должен использоваться отдельный адаптер.

Его назначение:

- скрыть технические детали ML-компонента от основной бизнес-логики;
- сформировать запрос модели;
- передать данные;
- получить результат;
- преобразовать ответ модели во внутренний формат приложения;
- обработать технические ошибки взаимодействия.

Основная прикладная логика должна взаимодействовать не непосредственно с реализацией модели, а с абстракцией сервиса прогнозирования.

Это позволит в дальнейшем заменить способ запуска модели без значительных изменений остальных компонентов системы.

## 8. ML-компонент

ML-компонент отвечает за операции, непосредственно связанные с моделью прогнозирования.

Основная ответственность:

- загрузка обученной модели;
- применение необходимых ML-преобразований;
- получение подготовленной временной последовательности;
- выполнение inference;
- формирование прогнозируемых значений;
- предоставление версии модели;
- обработка ошибок прогнозирования.

Обучение модели и рабочий inference должны рассматриваться как отдельные процессы.

Первая рабочая версия приложения может использовать предварительно обученную модель, а экспериментальная часть обучения может выполняться отдельными скриптами или ML-pipeline.

## 9. Уровень хранения данных

Хранилище должно обеспечивать сохранение данных, необходимых для работы приложения.

Минимально должны сохраняться:

- сведения о наборах данных;
- сведения о запусках прогнозирования;
- параметры запуска;
- прогнозируемые значения;
- фактические значения при наличии;
- рассчитанные метрики;
- версия модели;
- дата создания результата.

Конкретная технология хранения определяется на этапе технического проектирования.

## 10. Основные серверные модули

На логическом уровне Backend может быть разделён на следующие модули:

    dataset
    forecast
    history
    metrics
    ml
    common

### 10.1. dataset

Отвечает за:

- загрузку данных;
- валидацию;
- описание набора данных;
- подготовку данных.

### 10.2. forecast

Отвечает за:

- создание запуска прогнозирования;
- проверку параметров;
- запуск прогнозирования;
- получение результата;
- сохранение прогноза.

### 10.3. history

Отвечает за:

- получение списка прогнозов;
- получение подробной информации;
- фильтрацию истории.

### 10.4. metrics

Отвечает за расчёт:

- MAE;
- RMSE;
- MAPE;
- других экспериментально выбранных метрик.

### 10.5. ml

Содержит интерфейс взаимодействия с компонентом прогнозирования и соответствующий адаптер.

### 10.6. common

Содержит общие компоненты:

- ошибки;
- конфигурацию;
- журналирование;
- технические типы;
- общие вспомогательные средства.

## 11. Направление зависимостей

Внутренние зависимости должны быть организованы таким образом, чтобы прикладная логика не зависела напрямую от технических деталей внешних компонентов.

Упрощённая схема:

    Controller
        |
        v
    Application Service
        |
        +------> Repository abstraction
        |
        +------> Forecasting abstraction
                      |
                      v
                 ML Adapter

Такое разделение позволяет тестировать прикладную логику с использованием тестовых реализаций зависимостей.

## 12. Обработка ошибок

Ошибки должны разделяться как минимум на:

- ошибки пользовательского ввода;
- ошибки набора данных;
- ошибки бизнес-правил;
- ошибки взаимодействия с ML-компонентом;
- внутренние технические ошибки.

Backend должен преобразовывать ошибки в единый согласованный формат ответа.

Пользователь не должен получать необработанные stack trace или внутренние технические исключения.

## 13. Принципы расширения

Архитектура должна позволять:

- добавлять новые модели;
- заменять ML-компонент;
- добавлять новые источники данных;
- добавлять новые метрики;
- расширять визуализацию;
- добавлять новые варианты прогнозирования.

Расширение одного компонента по возможности не должно требовать значительных изменений в остальных компонентах.

## 14. Результат

Сформированная компонентная архитектура определяет базовое разделение ответственности между пользовательским интерфейсом, серверной частью, обработкой данных, хранилищем и ML-компонентом.

Следующим шагом является детализация потоков данных и последовательности взаимодействия компонентов в основных пользовательских сценариях.
