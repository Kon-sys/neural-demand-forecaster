# Контекст и границы системы

## 1. Назначение документа

Настоящий документ определяет контекст, границы и основные внешние взаимодействия программного средства прогнозирования потребительского спроса.

Документ используется как основа для дальнейшего проектирования внутренней архитектуры системы и позволяет определить, какие функции относятся к разрабатываемому программному средству, а какие остаются за пределами его ответственности.

## 2. Назначение системы

Разрабатываемое программное средство предназначено для формирования прогноза потребительского спроса на основании исторических данных о продажах с применением нейросетевых методов.

Система должна обеспечивать:

- загрузку исторических данных;
- проверку и предварительную обработку данных;
- подготовку данных для модели;
- формирование прогноза;
- расчёт показателей качества;
- хранение результатов;
- визуализацию прогнозируемых значений;
- просмотр истории прогнозирования;
- ведение пользовательского профиля;
- загрузку, замену и удаление фотографии профиля;
- административное управление пользователями;
- управление подразделениями и должностями.

Программное средство выполняет аналитические и вычислительные функции, но не принимает управленческие решения автоматически.

## 3. Пользователи системы

В системе выделяются два типа внешних участников: `USER` и `ADMIN`.

Пользователь с ролью `USER` взаимодействует с системой через пользовательский интерфейс и выполняет следующие действия:

- просматривает товары и исторические продажи;
- выбирает объект прогнозирования;
- задаёт параметры;
- запускает прогнозирование;
- анализирует полученный результат;
- просматривает историю предыдущих запусков;
- просматривает собственный профиль;
- изменяет имя, email и фотографию профиля;
- просматривает назначенные подразделение, должность и роль.

Пользователь не может самостоятельно изменять должность, подразделение, роль и статус учётной записи.

Пользователь с ролью `ADMIN` дополнительно:

- импортирует исторические продажи;
- управляет товарами;
- управляет пользователями;
- назначает пользователям должности;
- изменяет роли и статусы учётных записей;
- управляет подразделениями;
- управляет должностями и их привязкой к подразделениям.

Для работы с системой пользователю не требуется знание внутренней реализации нейросетевой модели.

## 4. Внешние источники данных

Исторические данные о продажах поступают в программное средство из внешнего источника.

В рамках первой версии системы основным способом получения данных является загрузка файла CSV.

В дальнейшем архитектура может быть расширена для поддержки:

- баз данных;
- ERP-систем;
- CRM-систем;
- внешних API;
- других структурированных источников данных.

Поддержка таких интеграций не является обязательной частью первой версии.

## 4.1. Внешнее объектное хранилище

Фотографии профиля пользователей хранятся во внешнем объектном хранилище.

Backend передаёт файл в объектное хранилище и сохраняет в PostgreSQL только URL изображения.

Frontend не должен содержать секретные ключи объектного хранилища и не взаимодействует с ним с использованием привилегированных учётных данных.

Конкретный поставщик объектного хранилища может быть выбран на этапе реализации. Допускается использование S3-совместимого сервиса или специализированного облачного файлового хранилища.

## 5. Граница системы

В границы разрабатываемого программного средства входят следующие функции:

- регистрация и авторизация;
- управление профилем пользователя;
- управление фотографией профиля;
- разграничение доступа по ролям и статусу учётной записи;
- административное управление пользователями;
- управление подразделениями;
- управление должностями и обязательной связью должности с подразделением;
- управление товарами;
- приём набора данных;
- валидация структуры и содержимого;
- предварительная обработка;
- формирование признаков;
- подготовка временных последовательностей;
- взаимодействие с моделью прогнозирования;
- получение прогнозных значений;
- расчёт метрик;
- хранение результатов;
- отображение аналитической информации.

## 6. Функции вне границ системы

В текущую версию системы не входят:

- управление закупками;
- автоматическое формирование заказов;
- управление поставщиками;
- управление складскими запасами;
- автоматическое изменение цен;
- финансовое планирование;
- полноценная ERP-функциональность;
- автоматическое получение организационной структуры из внешней HR/ERP-системы;
- сложная многоуровневая модель организационной подчинённости;
- автоматическое принятие бизнес-решений.

Система должна предоставлять информацию для поддержки принятия решений, а не заменять лицо, принимающее решение.

## 7. Основные внешние взаимодействия

В системе выделяются следующие основные потоки взаимодействия.

### 7.1. USER → программное средство

Пользователь передаёт:

- параметры прогнозирования;
- команды запуска прогнозирования;
- запросы на просмотр результатов и истории;
- изменения разрешённых полей профиля;
- фотографию профиля.

### 7.2. Программное средство → USER

Система предоставляет:

- профиль пользователя;
- назначенные подразделение и должность;
- сообщения об ошибках;
- состояние выполнения операций;
- прогнозируемые значения;
- графики;
- таблицы;
- показатели качества;
- историю запусков.

### 7.3. ADMIN → программное средство

Администратор дополнительно передаёт:

- CSV-файлы с историческими продажами;
- команды управления товарами;
- изменения роли и статуса пользователей;
- назначения должностей пользователям;
- данные подразделений;
- данные должностей и их принадлежности подразделениям.

### 7.4. Программное средство → ML-компонент

Прикладная часть передаёт:

- подготовленные входные данные;
- параметры прогнозирования;
- запрос на выполнение прогнозирования.

### 7.5. ML-компонент → программное средство

Компонент прогнозирования возвращает:

- прогнозируемые значения;
- информацию о версии модели;
- технический результат выполнения операции.

### 7.6. Программное средство ↔ объектное хранилище

Backend передаёт фотографии профиля в объектное хранилище и получает URL сохранённого объекта.

Frontend не выполняет привилегированные операции с объектным хранилищем напрямую.

## 8. Контекстная схема

Упрощённо контекст системы можно представить следующим образом:

    +----------------------+       +----------------------+
    |         USER         |       |        ADMIN         |
    +----------+-----------+       +----------+-----------+
               |                              |
               | профиль, прогнозы            | управление,
               | и запросы                    | CSV, оргструктура
               +---------------+--------------+
                               |
                               v
                 +------------------------------+
                 |                              |
                 |   Программное средство       |
                 |   прогнозирования спроса     |
                 |                              |
                 +---------+----------+---------+
                           |          |
                    данные |          | фотографии
                           v          v
                 +---------------+  +----------------------+
                 | ML-компонент  |  | Объектное хранилище |
                 +---------------+  +----------------------+

Исторические продажи в MVP поступают в систему из CSV, загружаемого администратором.

Данные пользователей, организационной структуры, товаров, продаж и прогнозов долговременно хранятся в PostgreSQL.

## 9. Архитектурные ограничения

При проектировании необходимо учитывать следующие ограничения:

- система разрабатывается в рамках учебного проекта;
- архитектура должна оставаться понятной и сопровождаемой;
- не следует использовать микросервисный подход без обоснованной необходимости;
- ML-компонент должен быть изолирован от пользовательского интерфейса;
- клиентская часть не должна обращаться напрямую к модели;
- бизнес-логика должна быть отделена от слоя представления;
- проверка административных прав, статуса пользователя и согласованности должности с подразделением должна выполняться на Backend;
- Frontend не должен хранить секреты объектного хранилища;
- компоненты должны быть организованы таким образом, чтобы модель можно было заменить без полной переработки приложения.

## 10. Результат

Определённые границы системы фиксируют ответственность разрабатываемого программного средства и позволяют перейти к проектированию его внутренней архитектуры.

На следующем уровне система должна быть декомпозирована на основные компоненты, отвечающие за пользовательский интерфейс, прикладную логику, работу с данными, хранение и прогнозирование.
