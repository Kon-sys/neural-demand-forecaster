# Поток данных и взаимодействие компонентов

## 1. Назначение документа

Настоящий документ описывает движение данных между компонентами программного средства при выполнении основных операций.

Цель документа — определить, какие данные передаются между уровнями системы и в какой последовательности выполняются ключевые процессы.

## 2. Общий поток данных

Основной поток прогнозирования выглядит следующим образом:

    CSV-файл
        |
        v
    Client
        |
        v
    Backend API
        |
        v
    Validation
        |
        v
    Preprocessing
        |
        v
    Forecasting Adapter
        |
        v
    ML Component
        |
        v
    Forecast Result
        |
        v
    Backend
        |
        +------> Persistence
        |
        v
    Client
        |
        v
    Charts / Tables / Metrics

## 3. Поток загрузки набора данных

### Шаг 1. Выбор файла

Пользователь выбирает CSV-файл в клиентском приложении.

### Шаг 2. Передача файла

Клиент отправляет файл в Backend API.

### Шаг 3. Первичная проверка

Backend выполняет первичную проверку:

- допустимого типа файла;
- допустимого размера;
- наличия содержимого.

### Шаг 4. Проверка структуры данных

Модуль обработки данных анализирует структуру файла.

Проверяются:

- обязательные столбцы;
- типы данных;
- корректность дат;
- числовые значения;
- пропущенные значения;
- дублирующиеся записи.

### Шаг 5. Обработка ошибок

При наличии критической ошибки Backend возвращает клиенту структурированную информацию о проблеме.

### Шаг 6. Регистрация набора данных

При успешной проверке система регистрирует набор данных и формирует его метаданные.

Минимальный набор метаданных:

    dataset_id
    file_name
    uploaded_at
    row_count
    date_from
    date_to
    validation_status

Дополнительно может сохраняться информация о доступных объектах прогнозирования.

### Шаг 7. Ответ клиенту

Клиент получает информацию об успешно зарегистрированном наборе данных.

## 4. Поток формирования прогноза

Для запуска прогнозирования клиент передаёт:

    dataset_id
    product_id
    forecast_horizon
    model_id или model_version — если применимо

После этого выполняется следующая последовательность.

### Шаг 1. Проверка параметров

Backend проверяет:

- существование указанного набора данных;
- наличие выбранного товара или другого объекта прогнозирования;
- корректность горизонта;
- достаточность исторических данных.

### Шаг 2. Получение исходных данных

Система получает необходимый временной ряд из выбранного набора данных.

### Шаг 3. Предварительная обработка

Выполняются предусмотренные pipeline-преобразования.

Они могут включать:

- сортировку;
- очистку данных;
- обработку пропусков;
- агрегирование;
- масштабирование;
- формирование временных признаков;
- подготовку входной последовательности.

Результатом является структура данных, пригодная для передачи компоненту прогнозирования.

### Шаг 4. Вызов Forecasting Adapter

Application Service обращается к абстракции прогнозирования.

Прикладная бизнес-логика не должна зависеть от конкретного способа запуска Python-модели или другой реализации ML-компонента.

### Шаг 5. Передача данных в ML-компонент

Adapter передаёт:

- подготовленные признаки;
- горизонт прогнозирования;
- параметры модели, если они необходимы;
- идентификатор или версию модели, если система поддерживает несколько моделей.

### Шаг 6. Выполнение inference

ML-компонент:

1. загружает необходимую версию модели;
2. применяет необходимые преобразования, относящиеся к ML-pipeline;
3. выполняет прогнозирование;
4. формирует результат в согласованном формате;
5. возвращает прогнозируемые значения и метаданные модели.

### Шаг 7. Формирование результата

Backend формирует объект результата прогнозирования.

Минимальный набор данных:

    forecast_id
    dataset_id
    product_id
    created_at
    forecast_horizon
    model_version
    forecast_values
    status

### Шаг 8. Расчёт метрик

Если для прогнозируемого периода доступны фактические значения, они передаются в сервис расчёта метрик.

Схема:

    actual_values
         |
         v
    Metrics Service
         |
         +--> MAE
         +--> RMSE
         +--> MAPE

Рассчитанные метрики связываются с конкретным прогнозом.

### Шаг 9. Сохранение результата

Результат сохраняется в хранилище.

Система должна сохранить данные, необходимые для последующего просмотра и анализа результата.

### Шаг 10. Ответ клиенту

Клиент получает:

- идентификатор прогноза;
- прогнозируемые значения;
- временную шкалу;
- метрики при их наличии;
- версию модели;
- параметры запуска.

## 5. Поток просмотра истории

Общая схема:

    User
      |
      v
    Client
      |
      | запрос истории
      v
    Backend
      |
      v
    Persistence
      |
      v
    Forecast summaries
      |
      v
    Client

Для списка истории достаточно передавать сокращённое представление:

    forecast_id
    product_id
    created_at
    forecast_horizon
    model_version
    metrics_summary

Подробные последовательности прогнозных значений могут загружаться только при открытии конкретного результата.

## 6. Поток просмотра отдельного результата

После выбора прогноза клиент запрашивает подробную информацию.

Backend получает:

- сведения о запуске;
- исторический временной ряд;
- прогнозируемые значения;
- фактические значения при наличии;
- рассчитанные метрики;
- информацию о модели.

Клиент использует полученные данные для формирования графиков, таблиц и информационных блоков.

## 7. Поток ошибок

### 7.1. Ошибка валидации

    Client
      |
      v
    Backend
      |
      v
    Validation
      |
      X
      |
      v
    Structured Error
      |
      v
    Client Notification

Система должна вернуть пользователю понятное описание проблемы без раскрытия внутренних технических деталей.

### 7.2. Ошибка ML-компонента

    Backend
      |
      v
    ML Adapter
      |
      v
    ML Component
      |
      X
      |
      v
    Adapter Error
      |
      v
    Application Error
      |
      +------> Technical Log
      |
      v
    Safe Response to Client

Отказ ML-компонента не должен приводить к повреждению ранее сохранённых данных или аварийному завершению всего приложения.

## 8. Формат API-взаимодействия

Основным форматом обмена структурированными данными между клиентом и сервером должен быть JSON.

Файлы передаются с использованием предусмотренного HTTP-механизма загрузки файлов.

Пример логического ответа после успешного прогнозирования:

    {
      "forecastId": "fc_001",
      "datasetId": "ds_001",
      "productId": "product_42",
      "forecastHorizon": 14,
      "modelVersion": "1.0.0",
      "values": [
        {
          "date": "2026-10-01",
          "value": 124.5
        }
      ],
      "metrics": {
        "mae": 8.2,
        "rmse": 10.4,
        "mape": 6.8
      }
    }

Приведённая структура является логическим примером и не фиксирует окончательный API-контракт.

Конкретные endpoint, DTO и правила обработки запросов должны быть определены на отдельном этапе проектирования API.

## 9. Идентификация сущностей

Для обеспечения прослеживаемости необходимо использовать отдельные идентификаторы для:

- набора данных;
- запуска прогнозирования;
- товара или другого объекта прогнозирования;
- модели;
- версии модели.

Это позволит однозначно определить, какие данные и какая версия модели использовались при формировании конкретного результата.

## 10. Воспроизводимость результатов

Для каждого запуска необходимо сохранять данные, достаточные для последующего анализа:

- идентификатор набора данных;
- параметры запуска;
- объект прогнозирования;
- горизонт;
- версию модели;
- дату и время запуска;
- рассчитанные метрики;
- прогнозируемые значения.

Если результат зависит от версии preprocessing-pipeline или его конфигурации, соответствующая версия также должна сохраняться.

Это позволит установить условия, при которых был получен конкретный прогноз.

## 11. Результат

Определённый поток данных устанавливает последовательность взаимодействия компонентов от загрузки исходного файла до отображения результатов прогнозирования.

Документ является основой для последующего проектирования:

- модели данных;
- API-контрактов;
- контракта взаимодействия с ML-компонентом;
- пользовательского интерфейса;
- интеграционных и системных тестов.
