# REST API программного средства

## 1. Назначение документа

Настоящий документ определяет логический REST API между клиентским приложением и Backend.

API обеспечивает работу с наборами данных, запуск прогнозирования, просмотр результатов и получение истории прогнозов.

Окончательные DTO могут уточняться в процессе реализации, однако изменения не должны нарушать ранее определённые функциональные требования.

## 2. Общие принципы

Базовый префикс API:

    /api/v1

Основным форматом структурированных запросов и ответов является JSON.

Загрузка файлов выполняется с использованием `multipart/form-data`.

Все даты и время в API должны передаваться в стандартизированном формате ISO 8601.

## 3. Структура успешного ответа

Для получения отдельных ресурсов Backend может возвращать непосредственно DTO ресурса.

Для операций создания используется HTTP-код `201 Created`.

Для успешного получения данных используется `200 OK`.

Для асинхронных операций при необходимости может использоваться `202 Accepted`.

## 4. Структура ошибки

Для ошибок должен использоваться единый формат.

Пример:

    {
      "code": "DATASET_VALIDATION_ERROR",
      "message": "Загруженный набор данных содержит ошибки",
      "details": [
        {
          "field": "date",
          "message": "Обнаружено некорректное значение даты"
        }
      ],
      "timestamp": "2026-09-18T12:00:00Z"
    }

Основные поля:

| Поле | Назначение |
| --- | --- |
| code | Машиночитаемый код ошибки |
| message | Понятное пользователю описание |
| details | Дополнительная информация |
| timestamp | Время возникновения |

## 5. Dataset API

### POST /api/v1/datasets

Загрузка нового набора данных.

Тип запроса:

    multipart/form-data

Параметр:

    file

Успешный ответ:

    201 Created

Пример:

    {
      "id": "ds_001",
      "fileName": "sales.csv",
      "uploadedAt": "2026-09-18T12:00:00Z",
      "rowCount": 42500,
      "dateFrom": "2023-01-01",
      "dateTo": "2026-08-31",
      "validationStatus": "VALID"
    }

Возможные ошибки:

- `400` — некорректный файл;
- `413` — превышен допустимый размер;
- `422` — набор имеет корректный формат передачи, но не подходит для обработки.

### GET /api/v1/datasets

Возвращает список доступных наборов данных.

Ответ:

    200 OK

### GET /api/v1/datasets/{datasetId}

Возвращает подробную информацию о наборе данных.

### GET /api/v1/datasets/{datasetId}/products

Возвращает доступные объекты прогнозирования.

Пример:

    [
      {
        "id": "product_42",
        "externalId": "SKU-42",
        "name": "Product 42",
        "category": "Category A"
      }
    ]

## 6. Forecast API

### POST /api/v1/forecasts

Создание нового запуска прогнозирования.

Запрос:

    {
      "datasetId": "ds_001",
      "productId": "product_42",
      "forecastHorizon": 14
    }

При наличии нескольких доступных моделей запрос может дополнительно содержать:

    modelVersionId

Успешный ответ:

    201 Created

Пример:

    {
      "id": "fc_001",
      "status": "PROCESSING",
      "createdAt": "2026-09-18T12:10:00Z"
    }

Если прогнозирование выполняется достаточно быстро, сервер может вернуть уже завершённый результат.

Если операция длительная, клиент получает идентификатор Forecast и далее проверяет его состояние.

### GET /api/v1/forecasts

Возвращает историю запусков.

Потенциальные параметры фильтрации:

    datasetId
    productId
    status
    dateFrom
    dateTo
    page
    size

Пример элемента списка:

    {
      "id": "fc_001",
      "productId": "product_42",
      "createdAt": "2026-09-18T12:10:00Z",
      "forecastHorizon": 14,
      "modelVersion": "1.0.0",
      "status": "COMPLETED",
      "metrics": {
        "mae": 8.2,
        "rmse": 10.4,
        "mape": 6.8
      }
    }

### GET /api/v1/forecasts/{forecastId}

Возвращает подробную информацию о прогнозе.

Пример:

    {
      "id": "fc_001",
      "datasetId": "ds_001",
      "productId": "product_42",
      "createdAt": "2026-09-18T12:10:00Z",
      "forecastHorizon": 14,
      "modelVersion": "1.0.0",
      "status": "COMPLETED",
      "values": [
        {
          "date": "2026-09-19",
          "value": 124.5
        },
        {
          "date": "2026-09-20",
          "value": 128.1
        }
      ],
      "metrics": {
        "mae": 8.2,
        "rmse": 10.4,
        "mape": 6.8
      }
    }

## 7. Forecast Status API

Если прогнозирование реализуется как длительная операция, статус может проверяться через:

    GET /api/v1/forecasts/{forecastId}

Поле `status` принимает одно из значений:

    PENDING
    PROCESSING
    COMPLETED
    FAILED

При статусе `FAILED` ответ должен содержать безопасную информацию об ошибке.

## 8. Metrics API

Отдельный endpoint для метрик необязателен, так как метрики могут возвращаться как часть Forecast.

При необходимости может использоваться:

    GET /api/v1/forecasts/{forecastId}/metrics

Ответ:

    {
      "mae": 8.2,
      "rmse": 10.4,
      "mape": 6.8,
      "calculatedAt": "2026-09-18T13:00:00Z"
    }

## 9. HTTP-коды

Основные используемые коды:

| Код | Назначение |
| --- | --- |
| 200 | Операция выполнена успешно |
| 201 | Ресурс создан |
| 202 | Запрос принят для последующей обработки |
| 400 | Некорректный запрос |
| 404 | Ресурс не найден |
| 409 | Конфликт текущего состояния |
| 413 | Файл превышает допустимый размер |
| 422 | Данные не могут быть обработаны |
| 500 | Внутренняя ошибка |
| 502 | Ошибка взаимодействия с зависимым сервисом |
| 503 | Зависимый компонент временно недоступен |

## 10. Пагинация

История прогнозов должна поддерживать пагинацию.

Параметры:

    page
    size

Ответ может содержать:

    {
      "items": [],
      "page": 0,
      "size": 20,
      "totalElements": 125,
      "totalPages": 7
    }

## 11. Валидация

Backend должен проверять:

- обязательные параметры;
- существование связанных сущностей;
- корректность горизонта;
- допустимость выбранного товара;
- пригодность Dataset для прогнозирования.

Клиентская валидация не заменяет серверную.

## 12. Версионирование API

Для предотвращения несовместимых изменений используется версия в URL:

    /api/v1

Несовместимые изменения API в будущем должны приводить к созданию новой версии, например:

    /api/v2

## 13. Результат

Определённый REST API формирует контракт взаимодействия между пользовательским интерфейсом и Backend и является основой для параллельной реализации клиентской и серверной частей.
