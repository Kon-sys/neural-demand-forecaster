# Пользовательские сценарии

## 1. Назначение документа

Документ определяет основные сценарии использования программного средства прогнозирования потребительского спроса.

Сценарии сформированы на основании границ системы и требований `FR-001` – `FR-106`.

Для каждого сценария определены:

- участник;
- цель;
- предусловия;
- основной поток;
- альтернативные потоки;
- результат.

---

# 2. Участники

## 2.1. USER

Обычный пользователь системы.

Основные возможности:

- авторизация;
- просмотр товаров;
- просмотр продаж;
- формирование прогноза;
- анализ результата;
- просмотр истории прогнозов;
- просмотр собственного профиля;
- изменение имени и email;
- загрузка, замена и удаление фотографии профиля;
- просмотр назначенной должности, подразделения и роли.

## 2.2. ADMIN

Администратор системы.

Наследует основные возможности пользователя и дополнительно может:

- создавать товары;
- редактировать товары;
- удалять товары;
- импортировать историю продаж из CSV;
- просматривать и администрировать пользователей;
- изменять роли и статусы пользователей;
- назначать должности;
- управлять подразделениями;
- управлять должностями и их обязательной привязкой к подразделениям.

## 2.3. ML-сервис

Внешний по отношению к Backend программный компонент, участвующий в сценарии прогнозирования.

## 2.4. Объектное хранилище

Внешний инфраструктурный компонент, используемый Backend для хранения бинарных файлов фотографий профиля.

---

# 3. UC-01. Регистрация

## Цель

Создать пользовательскую учётную запись.

## Основной участник

Незарегистрированный пользователь.

## Предусловия

Пользователь не авторизован.

## Основной сценарий

1. Пользователь открывает страницу регистрации.
2. Вводит требуемые данные.
3. Frontend проверяет форму.
4. Frontend отправляет данные Backend.
5. Backend выполняет серверную валидацию.
6. Backend проверяет уникальность учётной записи.
7. Backend хеширует пароль.
8. Backend создаёт пользователя с ролью `USER` и статусом `ACTIVE`.
9. Пользователь получает сообщение об успешной регистрации.
10. Пользователь может перейти к авторизации.

## Альтернативные сценарии

### Учётная запись уже существует

Backend возвращает ошибку конфликта.

Frontend отображает сообщение пользователю.

### Некорректные данные

Регистрация не выполняется.

Пользователь получает информацию об ошибочных полях.

## Результат

В системе создан новый пользователь с ролью `USER` и статусом `ACTIVE`.

---

# 4. UC-02. Авторизация

## Цель

Получить доступ к защищённым функциям системы.

## Основной участник

Зарегистрированный пользователь.

## Предусловия

Пользователь имеет активную учётную запись.

## Основной сценарий

1. Пользователь открывает страницу входа.
2. Вводит данные.
3. Frontend отправляет запрос Backend.
4. Backend находит пользователя.
5. Backend проверяет пароль.
6. Backend проверяет статус учётной записи.
7. Если статус равен `ACTIVE`, Backend формирует JWT.
8. Frontend получает данные сессии.
9. Пользователь перенаправляется в защищённую часть приложения.

## Альтернативные сценарии

### Неверные учётные данные

1. Backend отклоняет запрос.
2. JWT не выдаётся.
3. Пользователь получает сообщение об ошибке.

### Учётная запись заблокирована

1. Backend определяет статус `BLOCKED`.
2. JWT не выдаётся.
3. Пользователь получает сообщение о блокировке учётной записи.

## Результат

Пользователь авторизован.

---

# 5. UC-03. Управление товарами

## Цель

Управлять каталогом товаров.

## Основной участник

`ADMIN`.

## Предусловия

- администратор авторизован;
- JWT действителен;
- пользователь имеет роль `ADMIN`.

## Создание товара

1. Администратор открывает страницу товаров.
2. Выбирает добавление товара.
3. Вводит данные.
4. Backend проверяет значения.
5. Backend проверяет уникальность SKU.
6. Товар сохраняется.
7. Обновлённый список отображается пользователю.

## Редактирование

1. Администратор выбирает товар.
2. Открывает редактирование.
3. Изменяет данные.
4. Backend проверяет запрос.
5. Изменения сохраняются.

## Удаление

1. Администратор выбирает удаление.
2. Frontend запрашивает подтверждение.
3. Backend проверяет возможность удаления.
4. При отсутствии конфликтов товар удаляется.

## Альтернативные сценарии

- SKU уже существует;
- товар не найден;
- товар нельзя удалить из-за связанных данных;
- пользователь не имеет роли `ADMIN`.

## Результат

Каталог товаров изменён в соответствии с выполненной операцией.

---

# 7. UC-05. Импорт исторических продаж

## Цель

Массово загрузить историю продаж из CSV.

## Основной участник

`ADMIN`.

## Предусловия

- администратор авторизован;
- необходимые товары существуют;
- подготовлен CSV допустимого формата.

## Основной сценарий

1. Администратор открывает страницу импорта.
2. Выбирает CSV.
3. Frontend выполняет предварительную проверку расширения.
4. Файл передаётся Backend.
5. Backend проверяет тип и размер.
6. Backend читает CSV.
7. Проверяется структура.
8. Проверяются обязательные значения.
9. Выполняется сопоставление товаров.
10. Проверяются дубликаты.
11. Корректные данные сохраняются согласно выбранной стратегии импорта.
12. Backend формирует отчёт.
13. Frontend отображает результат.

## Альтернативные сценарии

### Некорректная структура

Импорт прекращается до изменения прикладных данных.

### Ошибочные строки

Ошибки включаются в отчёт импорта в соответствии с выбранной стратегией обработки.

### Неизвестный товар

Строка считается некорректной, если правила проекта не предусматривают автоматическое создание товара.

## Результат

История продаж обновлена, пользователь получил отчёт.

# 9. UC-07. Построение прогноза

## Цель

Сформировать прогноз спроса для выбранного товара.

## Основной участник

`USER` или `ADMIN`.

## Вспомогательный участник

ML-сервис.

## Предусловия

- пользователь авторизован;
- выбранный товар существует;
- имеется достаточная история продаж;
- Backend доступен;
- ML-сервис доступен.

## Основной сценарий

1. Пользователь открывает страницу прогнозирования.
2. Выбирает товар.
3. Указывает горизонт прогнозирования.
4. Запускает прогнозирование.
5. Frontend отправляет запрос Backend.
6. Backend проверяет параметры.
7. Backend получает историю продаж из PostgreSQL.
8. Backend проверяет достаточность данных.
9. Backend формирует запрос ML-сервису.
10. ML-сервис выполняет предобработку.
11. ML-сервис загружает рабочую модель.
12. ML-сервис выполняет inference.
13. ML-сервис возвращает прогноз.
14. Backend сохраняет Forecast.
15. Backend сохраняет ForecastValue.
16. Backend сохраняет доступные метрики.
17. Backend возвращает результат Frontend.
18. Frontend открывает страницу результата.

## Альтернативные сценарии

### Недостаточно данных

Прогнозирование прекращается.

Пользователь получает сообщение о недостаточности истории.

### ML-сервис недоступен

Backend завершает вызов по timeout и возвращает контролируемую ошибку.

### Ошибка модели

Результат не отмечается как успешно сформированный.

Пользователю возвращается безопасное сообщение.

## Результат

В системе существует сохранённый результат прогнозирования.

---

# 10. UC-08. Просмотр результата прогноза

## Цель

Проанализировать результат прогнозирования.

## Основной участник

`USER` или `ADMIN`.

## Предусловия

Существует успешно сформированный прогноз.

## Основной сценарий

1. Пользователь открывает результат.
2. Backend возвращает данные Forecast.
3. Backend возвращает связанные ForecastValue.
4. Frontend получает исторические значения.
5. На графике отображается история.
6. На графике отображается прогноз.
7. Отображается горизонт.
8. Отображается версия модели.
9. При наличии отображаются MAE, RMSE и MAPE.
10. Пользователь анализирует результат.

## Результат

Пользователь получил визуальное и числовое представление прогноза.

---

# 13. UC-11. Просмотр и изменение профиля

## Цель

Просмотреть собственный профиль и изменить разрешённые личные данные.

## Основной участник

`USER` или `ADMIN`.

## Предусловия

- пользователь авторизован;
- учётная запись имеет статус `ACTIVE`.

## Основной сценарий

1. Пользователь открывает страницу профиля.
2. Frontend запрашивает актуальные данные Backend.
3. Backend возвращает имя, email, фотографию, роль, статус, должность и подразделение должности.
4. Пользователь изменяет имя и/или email.
5. Frontend отправляет Backend только разрешённые для self-service поля.
6. Backend проверяет корректность данных и уникальность email.
7. Backend сохраняет изменения.
8. Frontend отображает обновлённый профиль.

## Ограничения

Пользователь не может через self-service сценарий изменять роль, статус, должность и подразделение.

## Результат

Разрешённые личные данные пользователя обновлены.

---

# 14. UC-12. Управление фотографией профиля

## Цель

Загрузить, заменить или удалить фотографию собственного профиля.

## Основной участник

`USER` или `ADMIN`.

## Вспомогательный участник

Объектное хранилище.

## Предусловия

Пользователь авторизован и имеет статус `ACTIVE`.

## Основной сценарий загрузки или замены

1. Пользователь выбирает изображение.
2. Frontend выполняет предварительную проверку файла.
3. Файл передаётся Backend как `multipart/form-data`.
4. Backend проверяет MIME-тип и размер.
5. Backend сохраняет изображение в объектном хранилище.
6. Объектное хранилище возвращает URL.
7. Backend сохраняет URL в профиле пользователя.
8. Frontend отображает новую фотографию.

## Сценарий удаления

1. Пользователь выбирает удаление фотографии.
2. Backend очищает `avatar_url` пользователя.
3. При предусмотренной политике Backend удаляет старый объект из хранилища либо ставит его на удаление.
4. Frontend отображает профиль без фотографии.

## Альтернативные сценарии

- неподдерживаемый MIME-тип;
- превышен допустимый размер файла;
- объектное хранилище недоступно;
- Backend недоступен.

## Результат

Фотография профиля обновлена или удалена без повреждения остальных данных пользователя.

---

# 15. UC-13. Административное управление пользователем

## Цель

Изменить административные атрибуты учётной записи.

## Основной участник

`ADMIN`.

## Предусловия

- администратор авторизован;
- его учётная запись имеет статус `ACTIVE`.

## Основной сценарий

1. Администратор открывает список пользователей.
2. Backend возвращает пользователей.
3. Администратор выбирает пользователя.
4. Система отображает его роль, статус, должность и подразделение должности.
5. Администратор изменяет допустимые административные атрибуты.
6. Backend проверяет полномочия и бизнес-ограничения.
7. Изменения сохраняются.
8. Frontend отображает актуальные данные.

## Ограничения

Система не позволяет:

- администратору заблокировать самого себя;
- администратору изменить собственную роль `ADMIN` на `USER`;
- заблокировать последнего активного администратора;
- изменить роль последнего активного администратора на `USER`.

## Результат

Административные данные пользователя обновлены.

# 17. UC-15. Управление должностями

## Цель

Вести справочник должностей с обязательной привязкой к подразделениям.

## Основной участник

`ADMIN`.

## Основной сценарий

1. Администратор открывает вкладку должностей.
2. Система отображает должности и связанные подразделения.
3. Администратор выбирает создание или редактирование.
4. Указывает наименование должности.
5. Обязательно выбирает подразделение.
6. Backend проверяет существование и допустимость подразделения.
7. Должность сохраняется.

## Бизнес-правила

- должность не может существовать без подразделения;
- каждая должность относится ровно к одному подразделению;
- деактивация не удаляет существующие пользовательские назначения;
- деактивированная должность не используется для новых назначений;
- если должность назначена пользователям, перенос должности в другое подразделение отклоняется до переназначения таких пользователей.

## Результат

Справочник должностей обновлён.

---

# 18. UC-16. Назначение должности пользователю

## Цель

Назначить пользователю должность, принадлежащую выбранному подразделению.

## Основной участник

`ADMIN`.

## Основной сценарий

1. Администратор открывает редактирование пользователя.
2. Выбирает подразделение в интерфейсе.
3. Frontend получает активные должности выбранного подразделения.
4. Администратор выбирает должность.
5. Frontend отправляет Backend идентификатор выбранной должности.
6. Backend по идентификатору должности проверяет:
    - существование должности;
    - активность должности;
    - наличие связанного подразделения;
    - активность связанного подразделения.
7. Backend сохраняет `position_id` пользователя.
8. Подразделение пользователя определяется через `position.department_id`.

## Альтернативный сценарий

Если администратор выбирает другое подразделение, несовместимая ранее выбранная должность очищается и должна быть выбрана заново.

## Результат

Пользователю назначена должность корректного подразделения.
