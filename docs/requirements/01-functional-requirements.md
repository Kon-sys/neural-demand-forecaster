# Функциональные требования

## 1. Назначение документа

Документ определяет функциональные требования к программному средству прогнозирования потребительского спроса.

Каждому требованию присвоен уникальный идентификатор вида `FR-XXX`, который должен использоваться при проектировании, реализации и тестировании системы.

## 2. Управление учётными записями

### FR-001. Регистрация пользователя

Система должна предоставлять возможность регистрации нового пользователя.

Для регистрации должны использоваться как минимум:

- имя или отображаемое имя;
- адрес электронной почты или иной выбранный уникальный логин;
- пароль.

После успешной регистрации пользователю должна назначаться роль `USER`.

### FR-002. Уникальность учётной записи

Система должна предотвращать создание двух пользователей с одинаковым уникальным идентификатором входа.

### FR-003. Проверка данных регистрации

Backend должен проверять обязательность и корректность данных регистрации.

### FR-004. Хеширование пароля

Пароль пользователя не должен сохраняться в базе данных в открытом виде.

### FR-005. Авторизация

Зарегистрированный пользователь должен иметь возможность выполнить вход с использованием своих учётных данных.

### FR-006. Выдача JWT

После успешной авторизации Backend должен выдавать данные, необходимые клиенту для выполнения защищённых запросов с использованием JWT.

### FR-007. Проверка JWT

Защищённые endpoint должны проверять наличие и корректность токена доступа.

### FR-008. Завершение пользовательской сессии

Frontend должен предоставлять возможность выйти из системы и удалить локальные данные активной сессии.

### FR-009. Роли пользователей

Система должна поддерживать роли:

- `USER`;
- `ADMIN`.

### FR-010. Ограничение административных операций

Операции, доступные только администратору, должны блокироваться для пользователя с ролью `USER` как на уровне интерфейса, так и на уровне Backend.

## 3. Управление товарами

### FR-011. Получение списка товаров

Авторизованный пользователь должен иметь возможность получить список товаров.

### FR-012. Просмотр товара

Авторизованный пользователь должен иметь возможность получить информацию об отдельном товаре.

### FR-013. Создание товара

Пользователь с ролью `ADMIN` должен иметь возможность создать товар.

### FR-014. Редактирование товара

Пользователь с ролью `ADMIN` должен иметь возможность изменить данные существующего товара.

### FR-015. Удаление товара

Пользователь с ролью `ADMIN` должен иметь возможность удалить товар, если операция не нарушает ограничения целостности данных.

### FR-016. Уникальность SKU

Если для товара используется SKU или другой внешний идентификатор, его значение должно быть уникальным.

### FR-017. Поиск товаров

Система должна предоставлять возможность поиска товаров по основным идентифицирующим атрибутам.

## 4. Работа с продажами

### FR-018. Хранение продаж

Система должна сохранять исторические данные о продажах в PostgreSQL.

### FR-019. Получение истории продаж

Авторизованный пользователь должен иметь возможность просматривать историю продаж.

### FR-020. Фильтрация по товару

История продаж должна поддерживать фильтрацию по товару.

### FR-021. Фильтрация по периоду

История продаж должна поддерживать фильтрацию по диапазону дат.

### FR-022. Пагинация

При объёме данных, при котором вывод всех записей одновременно становится нецелесообразным, API истории продаж должен поддерживать пагинацию.

## 5. Импорт CSV

### FR-023. Загрузка CSV

Пользователь с ролью `ADMIN` должен иметь возможность загрузить CSV-файл с историческими продажами.

### FR-024. Проверка типа файла

Система должна проверять допустимость типа загружаемого файла.

### FR-025. Проверка структуры CSV

Система должна проверять наличие обязательных столбцов.

### FR-026. Проверка значений

Система должна проверять корректность значений обязательных полей.

### FR-027. Проверка товара

Система должна проверять возможность сопоставления импортируемой продажи с существующим товаром.

### FR-028. Обработка дубликатов

Система должна обнаруживать дублирующиеся записи в соответствии с выбранным правилом идентификации дублей.

### FR-029. Атомарность критической ошибки

Критическая ошибка обработки файла не должна приводить к частично неконтролируемому изменению данных.

### FR-030. Отчёт об импорте

После завершения операции система должна сформировать результат импорта.

Он должен содержать как минимум:

- количество обработанных строк;
- количество успешно импортированных строк;
- количество пропущенных строк;
- количество строк с ошибками.

### FR-031. Информация об ошибочных строках

При наличии некорректных строк пользователь должен получить информацию, позволяющую определить причину ошибки.

## 6. Формирование прогноза

### FR-032. Выбор товара

Пользователь должен иметь возможность выбрать товар, для которого строится прогноз.

### FR-033. Выбор горизонта прогнозирования

Пользователь должен иметь возможность указать допустимый горизонт прогнозирования.

### FR-034. Проверка достаточности истории

Перед вызовом модели система должна проверить наличие достаточного количества исторических данных.

### FR-035. Получение исторических данных

Backend должен получить необходимые данные о продажах выбранного товара из PostgreSQL.

### FR-036. Вызов ML-сервиса

Backend должен передать необходимые данные и параметры в ML-сервис через предусмотренный API.

### FR-037. Обработка недоступности ML-сервиса

Недоступность ML-сервиса должна обрабатываться как контролируемая ошибка и не должна приводить к аварийному завершению Backend.

### FR-038. Формирование прогнозных значений

ML-сервис должен возвращать прогнозируемые значения спроса на указанный горизонт.

### FR-039. Версия модели

Результат прогнозирования должен позволять определить версию модели, использованную при его формировании.

### FR-040. Сохранение прогноза

Успешно сформированный прогноз должен сохраняться в PostgreSQL.

### FR-041. Сохранение значений прогноза

Отдельные прогнозируемые значения должны быть связаны с соответствующим запуском прогнозирования.

### FR-042. Автор прогноза

Сохранённый прогноз должен позволять определить пользователя, инициировавшего запуск.

## 7. Метрики качества

### FR-043. Расчёт MAE

Система должна поддерживать расчёт MAE при наличии необходимых фактических данных.

### FR-044. Расчёт RMSE

Система должна поддерживать расчёт RMSE при наличии необходимых фактических данных.

### FR-045. Расчёт MAPE

Система должна поддерживать расчёт MAPE при наличии необходимых фактических данных.

### FR-046. Отображение метрик

Доступные показатели качества должны отображаться пользователю на странице результата прогнозирования.

## 8. Просмотр результата

### FR-047. Получение результата

Пользователь должен иметь возможность открыть сохранённый прогноз.

### FR-048. Отображение параметров

На странице результата должны отображаться основные параметры запуска.

### FR-049. Исторические значения

Система должна предоставлять данные, необходимые для отображения исторического спроса.

### FR-050. Прогнозируемые значения

Система должна предоставлять прогнозируемые значения с привязкой ко времени.

### FR-051. График

Frontend должен отображать исторические и прогнозируемые значения в графической форме.

### FR-052. Числовое представление

Прогнозируемые значения должны быть доступны не только на графике, но и в числовом представлении.

## 9. История прогнозов

### FR-053. Получение истории

Авторизованный пользователь должен иметь возможность получить историю доступных ему прогнозов.

### FR-054. Основные сведения

Для каждого элемента истории должны отображаться как минимум:

- товар;
- дата запуска;
- горизонт прогнозирования;
- статус.

### FR-055. Открытие результата

Пользователь должен иметь возможность перейти из истории к подробному результату.

### FR-056. Фильтрация истории

История прогнозов должна поддерживать предусмотренную проектом фильтрацию.

### FR-057. Пустое состояние

Frontend должен корректно отображать состояние, при котором история прогнозов отсутствует.

## 10. Состояния длительных операций

### FR-058. Индикация загрузки

Frontend должен отображать состояние выполнения операций, которые не завершаются мгновенно.

### FR-059. Статус прогнозирования

Если формирование прогноза выполняется асинхронно или занимает заметное время, пользователь должен видеть текущее состояние операции.

## 11. Обработка ошибок

### FR-060. Единый формат API-ошибок

Backend должен возвращать ошибки в едином структурированном формате.

### FR-061. Понятные сообщения

Frontend должен отображать пользователю понятное описание возникшей проблемы.

### FR-062. Скрытие технических деталей

Пользователь не должен получать необработанные stack trace и другую внутреннюю техническую информацию.

### FR-063. Сохранность существующих данных

Ошибка новой операции не должна повреждать ранее корректно сохранённые данные.

## 12. Health Check

### FR-064. Backend Health Check

Backend должен предоставлять техническую возможность проверки своей работоспособности.

### FR-065. ML Health Check

ML-сервис должен предоставлять endpoint `/health`.

### FR-066. ML Predict

ML-сервис должен предоставлять endpoint `/predict` для выполнения прогнозирования.

## 13. Результат

Определённые функциональные требования фиксируют обязательное поведение MVP и являются основой для пользовательских сценариев, архитектуры, REST API, проектирования базы данных и тестирования.
