# Функциональные требования

## 1. Назначение документа

Настоящий документ определяет функциональные требования к программному средству прогнозирования потребительского спроса на основе нейросетевых методов.

Функциональные требования описывают операции, которые должна обеспечивать система для выполнения целевого процесса прогнозирования, определённого в модели TO-BE.

## 2. Основные функциональные области

В программном средстве выделяются следующие функциональные области:

1. управление исходными данными;
2. проверка и предварительная обработка данных;
3. настройка параметров прогнозирования;
4. формирование прогноза;
5. оценка качества прогнозирования;
6. хранение результатов;
7. визуализация и анализ результатов;
8. просмотр истории прогнозирования.

## 3. Требования к работе с исходными данными

### FR-01. Загрузка набора данных

Система должна предоставлять пользователю возможность загрузить набор исторических данных о продажах.

На первоначальном этапе должна поддерживаться загрузка структурированных данных из файла CSV.

### FR-02. Проверка структуры данных

После загрузки система должна автоматически проверять соответствие набора данных ожидаемой структуре.

Проверка должна включать:

- наличие обязательных полей;
- корректность типов данных;
- корректность дат;
- наличие числовых значений в количественных полях.

### FR-03. Обнаружение некорректных данных

Система должна обнаруживать:

- пропущенные обязательные значения;
- дублирующиеся записи;
- некорректные даты;
- некорректные числовые значения;
- записи, которые невозможно использовать для прогнозирования.

### FR-04. Отображение результата проверки

Система должна информировать пользователя о результате проверки загруженного набора данных.

При обнаружении критических ошибок система должна указывать причины, препятствующие дальнейшей обработке.

## 4. Требования к подготовке данных

### FR-05. Предварительная обработка

Система должна выполнять предварительную обработку данных перед их передачей модели прогнозирования.

Обработка может включать:

- сортировку по времени;
- удаление или обработку некорректных записей;
- обработку пропущенных значений;
- агрегирование данных;
- масштабирование признаков;
- преобразование входных признаков.

### FR-06. Формирование временных признаков

Система должна обеспечивать возможность формирования признаков, связанных со временем.

К таким признакам могут относиться:

- день;
- неделя;
- месяц;
- квартал;
- день недели;
- сезонные признаки.

### FR-07. Формирование входных последовательностей

Система должна формировать временные последовательности требуемой длины для передачи нейросетевой модели.

## 5. Требования к настройке прогнозирования

### FR-08. Выбор объекта прогнозирования

Система должна предоставлять возможность выбрать товар или иной доступный объект, для которого необходимо построить прогноз.

### FR-09. Выбор горизонта прогнозирования

Пользователь должен иметь возможность задать период, на который необходимо получить прогноз.

Допустимые значения горизонта прогнозирования должны определяться возможностями используемой модели и доступностью исторических данных.

### FR-10. Выбор модели

Если в системе доступно несколько моделей прогнозирования, пользователь или системная конфигурация должны определять модель, используемую для конкретного запуска.

## 6. Требования к формированию прогноза

### FR-11. Запуск прогнозирования

Система должна предоставлять пользователю возможность инициировать процесс формирования прогноза.

### FR-12. Использование подготовленных данных

При прогнозировании система должна использовать данные, прошедшие предусмотренную предварительную обработку.

### FR-13. Формирование прогнозных значений

Система должна формировать последовательность прогнозируемых значений спроса для выбранного объекта и заданного горизонта прогнозирования.

### FR-14. Регистрация параметров запуска

Для каждого запуска система должна сохранять параметры, необходимые для идентификации результата.

К ним относятся:

- дата и время запуска;
- объект прогнозирования;
- горизонт прогнозирования;
- версия модели;
- используемый набор данных или его идентификатор.

## 7. Требования к оценке качества

### FR-15. Расчёт метрик

При наличии фактических значений система должна обеспечивать расчёт метрик качества прогнозирования.

Основными метриками являются:

- MAE;
- RMSE;
- MAPE.

### FR-16. Хранение метрик

Рассчитанные показатели качества должны сохраняться вместе с соответствующим результатом прогнозирования.

### FR-17. Сравнение прогнозируемых и фактических значений

При наличии фактических данных система должна предоставлять возможность сравнения прогнозируемого и фактического спроса.

## 8. Требования к хранению результатов

### FR-18. Сохранение прогноза

Каждый успешно сформированный прогноз должен сохраняться системой.

### FR-19. Хранение истории

Система должна хранить историю выполненных прогнозов.

### FR-20. Просмотр сохранённого прогноза

Пользователь должен иметь возможность открыть ранее сформированный прогноз и просмотреть:

- параметры запуска;
- прогнозируемые значения;
- фактические значения при их наличии;
- используемую версию модели;
- показатели качества.

## 9. Требования к визуализации

### FR-21. Графическое представление исторических данных

Система должна отображать исторические значения спроса в графической форме.

### FR-22. Графическое представление прогноза

Прогнозируемые значения должны отображаться на графике с привязкой ко времени.

### FR-23. Совместное отображение данных

Система должна обеспечивать возможность совместного отображения исторических и прогнозируемых значений.

При наличии фактических значений они также должны отображаться для сравнения.

### FR-24. Табличное представление

Система должна предоставлять прогнозные значения в табличной форме.

### FR-25. Отображение метрик

Рассчитанные метрики качества должны отображаться пользователю вместе с результатами прогнозирования.

## 10. Требования к обработке ошибок

### FR-26. Ошибки входных данных

Система должна прекращать запуск прогнозирования при обнаружении критических ошибок входных данных.

### FR-27. Ошибки модели

При невозможности выполнения прогнозирования система должна информировать пользователя об ошибке без завершения работы всего приложения.

### FR-28. Понятные сообщения об ошибках

Сообщения об ошибках должны содержать понятное пользователю описание причины проблемы.

Техническая информация, не предназначенная для пользователя, должна регистрироваться отдельно.

## 11. Границы функциональности

В рамках текущей версии программного средства не предусматривается автоматическое:

- управление закупками;
- формирование заказов поставщикам;
- изменение складских запасов;
- управление ценами;
- принятие управленческих решений.

Система формирует прогноз и предоставляет аналитическую информацию, а решение на основании полученных результатов принимает пользователь.

## 12. Результат

Определённые функциональные требования формируют перечень возможностей, которые должны быть реализованы в программном средстве.

На их основе должны быть сформированы архитектура системы, пользовательские сценарии, интерфейсы взаимодействия и критерии последующего тестирования.
