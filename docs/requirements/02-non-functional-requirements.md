# Нефункциональные требования

## 1. Назначение документа

Документ определяет нефункциональные требования к программному средству прогнозирования потребительского спроса.

Каждому требованию присвоен идентификатор вида `NFR-XXX`.

## 2. Безопасность

### NFR-001. Хранение паролей

Пароли пользователей должны храниться только в виде криптографического хеша.

### NFR-002. JWT

Доступ к защищённым ресурсам должен выполняться только после успешной проверки JWT.

### NFR-003. Разграничение доступа

Backend должен самостоятельно проверять права пользователя независимо от ограничений, реализованных во Frontend.

### NFR-004. Роль по умолчанию

Публичная регистрация должна создавать пользователя только с ролью `USER`.

### NFR-005. Секреты

Пароли базы данных, JWT-секреты и другие конфиденциальные параметры не должны храниться непосредственно в Git-репозитории.

### NFR-006. Переменные окружения

Конфиденциальная конфигурация должна передаваться через переменные окружения или иной безопасный механизм конфигурации.

### NFR-007. CORS

Backend должен использовать явную конфигурацию допустимых источников CORS.

### NFR-008. HTTPS

При развёртывании системы вне локальной среды передача пользовательских данных и токенов должна выполняться через HTTPS.

### NFR-009. Проверка пользовательского ввода

Backend должен проверять все входные данные независимо от клиентской валидации.

### NFR-010. Ограничение загрузки

Для загружаемых CSV-файлов должен быть установлен контролируемый предел размера.

Конкретное значение определяется конфигурацией приложения и проверяется в рамках тестирования.

### NFR-011. Секреты в журналах

Пароли, JWT и другие секреты не должны записываться в журналы приложения.

## 3. Надёжность

### NFR-012. Изоляция ошибок

Ошибка одного запроса не должна приводить к аварийному завершению всего Backend.

### NFR-013. Недоступность ML

Недоступность ML-сервиса должна обрабатываться контролируемо.

### NFR-014. Сохранность данных

Неуспешная операция не должна повреждать ранее успешно сохранённые данные.

### NFR-015. Транзакционность

Операции, изменяющие несколько связанных записей и требующие атомарности, должны выполняться в транзакции.

### NFR-016. Целостность БД

База данных должна использовать первичные ключи, внешние ключи, ограничения и другие механизмы обеспечения целостности.

### NFR-017. Предсказуемая обработка ошибок

Одинаковые категории ошибок должны обрабатываться единообразно.

## 4. Производительность

### NFR-018. Обычные API-запросы

Запросы, не выполняющие импорт больших файлов, обучение или ML-inference, должны обеспечивать приемлемое для интерактивного веб-приложения время ответа.

В рамках тестовой среды проекта целевым ориентиром является выполнение стандартных CRUD-запросов не более чем за 2 секунды при штатной нагрузке.

### NFR-019. Длительные операции

Продолжительные операции не должны создавать впечатление зависания интерфейса.

Frontend должен показывать индикатор выполнения.

### NFR-020. Прогнозирование

Продолжительность inference должна измеряться экспериментально и фиксироваться при тестировании итоговой модели.

### NFR-021. Пагинация

Большие коллекции данных должны загружаться порциями, если передача всего набора приводит к существенному ухудшению работы интерфейса.

## 5. Резервное копирование

### NFR-022. Создание резервной копии

Для PostgreSQL должен быть предусмотрен воспроизводимый механизм создания резервной копии.

### NFR-023. Восстановление

Должен быть предусмотрен механизм восстановления PostgreSQL из созданной резервной копии.

### NFR-024. Проверка восстановления

Работоспособность процедуры восстановления должна быть проверена до завершения проекта.

### NFR-025. Хранение дампов

Файлы резервных копий не должны случайно добавляться в Git-репозиторий.

### NFR-026. Документирование

README или отдельная эксплуатационная документация должны содержать инструкции по созданию и восстановлению резервной копии.

## 6. Удобство использования

### NFR-027. Единообразный интерфейс

Страницы приложения должны использовать согласованные правила оформления и взаимодействия.

### NFR-028. Понятность основных операций

Для выполнения типового сценария пользователь не должен знать детали реализации Backend или ML-модели.

### NFR-029. Состояние загрузки

Для запросов, требующих ожидания, интерфейс должен отображать состояние загрузки.

### NFR-030. Ошибки форм

Ошибки пользовательского ввода должны отображаться рядом с соответствующим полем либо другим однозначно понятным способом.

### NFR-031. Пустые состояния

Страницы со списками должны корректно отображаться при отсутствии данных.

### NFR-032. Подтверждение опасных операций

Необратимые или потенциально опасные пользовательские действия должны требовать подтверждения, если это уместно.

## 7. Сопровождаемость

### NFR-033. Разделение компонентов

Frontend, Backend, ML-сервис и инфраструктурные материалы должны иметь чётко разделённую ответственность.

### NFR-034. Модульность Backend

Backend должен быть разделён на логические модули по предметным областям.

### NFR-035. Изоляция ML

Backend не должен зависеть от внутренней реализации нейросетевой модели.

### NFR-036. Конфигурация

Параметры окружения не должны быть жёстко зафиксированы в исходном коде.

### NFR-037. Документация запуска

Каждый исполняемый компонент должен иметь достаточную документацию для локального запуска.

### NFR-038. Миграции БД

Изменения схемы PostgreSQL должны выполняться воспроизводимым механизмом миграций.

## 8. Тестируемость

### NFR-039. Backend

Критическая бизнес-логика Backend должна допускать автоматизированное тестирование.

### NFR-040. REST API

Ключевые API-сценарии должны быть проверены тестами.

### NFR-041. Импорт CSV

Валидация и обработка CSV должны допускать автоматизированное тестирование.

### NFR-042. ML preprocessing

Конвейер подготовки данных должен допускать воспроизводимое тестирование.

### NFR-043. ML API

Endpoint ML-сервиса должны быть проверены автоматизированными тестами.

### NFR-044. Интеграционный сценарий

Должен быть проверен полный путь:

`Frontend → Backend → PostgreSQL → ML-сервис → Backend → Frontend`.

## 9. Воспроизводимость ML

### NFR-045. Разделение данных

Train, validation и test должны разделяться таким образом, чтобы будущие наблюдения не попадали в данные, используемые для обучения.

### NFR-046. Версия модели

Использованная версия итоговой модели должна быть определима для сохранённого прогноза.

### NFR-047. Повторяемая предобработка

Операции подготовки данных при inference должны соответствовать преобразованиям, использованным при обучении.

### NFR-048. Сохранение модели

Обученная итоговая модель должна сохраняться в форме, позволяющей повторно загрузить её без нового обучения.

## 10. Журналирование

### NFR-049. Backend logging

Backend должен регистрировать основные технические события и ошибки.

### NFR-050. ML logging

ML-сервис должен регистрировать запуск, ошибки загрузки модели и ошибки inference.

### NFR-051. Корреляция ошибок

Для сложных межкомпонентных операций должна существовать возможность связать Backend-запрос с соответствующим обращением к ML-сервису.

## 11. Совместимость и эксплуатация

### NFR-052. Конфигурация окружения

Для локального запуска должны быть предусмотрены примеры необходимых переменных окружения.

### NFR-053. Чистое развёртывание

Проект должен разворачиваться по документации из чистого рабочего окружения при наличии требуемых зависимостей.

### NFR-054. Независимый запуск компонентов

Frontend, Backend и ML-сервис должны иметь явно определённые команды запуска.

### NFR-055. Health Check

Backend и ML-сервис должны предоставлять возможность технической проверки их состояния.

## 12. Ограничение сложности

### NFR-056. Соответствие масштабу проекта

Архитектура должна соответствовать масштабу курсовой работы и не использовать сложную инфраструктуру без функциональной необходимости.

### NFR-057. Расширяемость

Структура программного средства должна позволять в дальнейшем:

- заменять ML-модель;
- добавлять новые модели;
- расширять состав признаков;
- добавлять новые способы импорта;
- развивать пользовательский интерфейс.

Это не означает обязательную реализацию перечисленных расширений в MVP.

## 13. Результат

Сформированные нефункциональные требования определяют ожидаемые характеристики безопасности, надёжности, производительности, удобства использования, сопровождаемости, тестируемости и эксплуатации программного средства.

Требования должны учитываться при проектировании архитектуры и проверяться в соответствующих этапах реализации и тестирования.
