# Границы программной системы

## 1. Назначение документа

Документ определяет функциональные границы программного средства прогнозирования потребительского спроса, состав минимально жизнеспособной версии системы (MVP), роли пользователей, ограничения проекта и критерии его готовности.

Зафиксированные границы используются при формировании требований, проектировании архитектуры, базы данных, пользовательского интерфейса и последующей реализации программного средства.

## 2. Назначение программного средства

Разрабатываемое программное средство предназначено для хранения и анализа исторических данных о продажах, формирования прогноза потребительского спроса с применением нейросетевой модели и предоставления результатов пользователю в графической и числовой форме.

Система должна поддерживать полный пользовательский сценарий от загрузки исторических данных до получения и просмотра результата прогнозирования.

Прогноз используется как средство информационной поддержки пользователя. Программное средство не принимает управленческие решения автоматически.

## 3. Состав MVP

В минимально жизнеспособную версию программного средства входят следующие функциональные области:

1. регистрация и авторизация пользователей;
2. разграничение доступа по ролям `USER` и `ADMIN`;
3. управление каталогом товаров;
4. хранение истории продаж;
5. импорт исторических данных о продажах из CSV;
6. просмотр и фильтрация продаж;
7. формирование прогноза спроса по выбранному товару;
8. применение ML-модели для прогнозирования;
9. расчёт показателей качества прогнозирования;
10. сохранение результатов прогнозирования;
11. просмотр отдельного результата;
12. просмотр истории прогнозов;
13. графическое представление исторических и прогнозируемых значений;
14. просмотр и изменение личного профиля пользователя;
15. загрузка, замена и удаление фотографии профиля;
16. административное управление пользователями;
17. управление организационной структурой — подразделениями и должностями;
18. блокировка и разблокировка учётных записей;
19. обработка ошибок и нештатных ситуаций;
20. журналирование основных технических событий;
21. резервное копирование и восстановление PostgreSQL.

## 4. Роли пользователей

В системе предусматриваются две роли:

- `USER`;
- `ADMIN`.

### 4.1. USER

Пользователь с ролью `USER` предназначен для выполнения основных аналитических операций.

Пользователь должен иметь возможность:

- зарегистрироваться;
- выполнить вход в систему;
- завершить пользовательскую сессию;
- просматривать список товаров;
- просматривать исторические продажи;
- применять доступные фильтры к истории продаж;
- выбирать товар для прогнозирования;
- задавать доступные параметры прогноза;
- запускать прогнозирование;
- просматривать сформированный прогноз;
- просматривать показатели качества модели;
- просматривать историю прогнозов;
- открывать ранее сформированный результат;
- просматривать собственный профиль;
- изменять собственные имя и email;
- загружать, заменять и удалять фотографию профиля;
- просматривать назначенные подразделение и должность;
- просматривать собственную роль.

Пользователь не может самостоятельно изменять:

- подразделение;
- должность;
- роль;
- статус учётной записи.

Организационные атрибуты пользователя изменяются только администратором.

### 4.2. ADMIN

Пользователь с ролью `ADMIN` обладает возможностями обычного пользователя и дополнительными функциями управления данными.

Администратор должен иметь возможность:

- создавать товары;
- изменять товары;
- удалять товары при отсутствии ограничений целостности данных;
- выполнять импорт исторических продаж из CSV;
- просматривать результат импорта;
- анализировать ошибки некорректных строк CSV;
- просматривать список пользователей;
- изменять роль пользователя между `USER` и `ADMIN`;
- блокировать и разблокировать учётные записи;
- назначать и изменять должность пользователя;
- создавать и редактировать подразделения;
- активировать и деактивировать подразделения;
- создавать и редактировать должности;
- привязывать должность к подразделению;
- изменять подразделение, к которому относится должность;
- активировать и деактивировать должности;
- выполнять остальные функции, доступные роли `USER`.

При назначении должности пользователю администратор сначала выбирает подразделение. Интерфейс должен предлагать только активные должности выбранного подразделения.

Администратор не может:

- заблокировать собственную учётную запись;
- снять с собственной учётной записи роль `ADMIN`;
- заблокировать последнего активного администратора;
- изменить роль последнего активного администратора на `USER`.

Самостоятельная регистрация пользователя с ролью `ADMIN` не предусматривается.

Способ создания первоначального администратора определяется на этапе реализации и конфигурации системы.

## 5. Основные объекты системы

В рамках MVP выделяются следующие основные предметные сущности:

- пользователь;
- подразделение;
- должность;
- товар;
- продажа;
- прогноз;
- значение прогноза.

Пользователь содержит учётные данные, роль, статус учётной записи, ссылку на фотографию профиля и назначенную должность.

Подразделение представляет элемент организационной структуры и имеет признак активности.

Должность обязательно относится ровно к одному подразделению и также имеет признак активности. Создание должности без подразделения не допускается.

Подразделение пользователя определяется через назначенную должность. При изменении подразделения в административном интерфейсе должна быть выбрана должность, принадлежащая этому подразделению.

Подразделения и должности в рамках MVP не удаляются физически. Деактивация сохраняет существующие назначения, но исключает значение из новых назначений.

Дополнительные технические сущности могут быть введены на этапе проектирования базы данных, если они необходимы для обеспечения целостности, журналирования, хранения параметров модели или воспроизводимости результатов.

## 6. Исторические данные о продажах

Исторические данные должны храниться в PostgreSQL.

Для каждой продажи минимально необходимо определить:

- товар;
- дату;
- количество проданных единиц.

Дополнительные атрибуты могут использоваться при наличии соответствующих данных и обоснованной необходимости.

Основным механизмом массовой загрузки исторических продаж в MVP является импорт CSV.

## 7. Импорт CSV

Система должна поддерживать импорт исторических продаж из CSV-файла.

Во время импорта необходимо:

- проверить тип файла;
- проверить структуру;
- проверить наличие обязательных столбцов;
- проверить значения;
- обнаружить некорректные строки;
- обработать дублирующиеся данные;
- сформировать результат импорта.

Некорректность отдельных строк не должна приводить к неконтролируемому повреждению уже сохранённых данных.

## 8. Прогнозирование

Пользователь должен иметь возможность сформировать прогноз спроса для выбранного товара.

Для построения прогноза система использует исторические данные о продажах, хранящиеся в PostgreSQL.

Основная серверная часть получает необходимые данные и передаёт их ML-сервису.

ML-сервис выполняет подготовку данных, необходимую для модели, и формирует прогноз.

Backend сохраняет полученный результат и предоставляет его Frontend.

## 9. Интеллектуальная составляющая

В рамках проекта должны быть реализованы и исследованы как минимум:

- простая baseline-модель;
- нейросетевая модель LSTM.

Модели должны оцениваться на одинаковых тестовых данных.

Основными метриками качества являются:

- MAE;
- RMSE;
- MAPE.

По результатам экспериментов должно быть выполнено сравнение моделей и обоснован выбор итогового подхода.

Рабочая ML-модель предоставляется основной системе через отдельный ML-сервис.

## 10. Компоненты программной системы

В состав итогового программного решения должны входить:

- Frontend;
- Backend;
- ML-сервис;
- PostgreSQL;
- внешнее объектное хранилище фотографий профиля.

Основное назначение компонентов:

### Frontend

Отвечает за пользовательский интерфейс и взаимодействие пользователя с системой.

### Backend

Отвечает за бизнес-логику, авторизацию, управление данными, взаимодействие с PostgreSQL и координацию процесса прогнозирования.

### ML-сервис

Отвечает за применение обученной модели и операции, непосредственно связанные с ML-pipeline.

### PostgreSQL

Используется для долговременного хранения прикладных данных системы, включая пользователей, организационную структуру и URL фотографий профиля.

### Объектное хранилище

Используется для хранения бинарных файлов фотографий пользователей.

В PostgreSQL сохраняется только URL изображения. Frontend не получает секретные ключи объектного хранилища и не обращается к нему с привилегированными учётными данными. Загрузка фотографии в production-варианте выполняется через Backend.

## 11. Функции вне границ проекта

В текущую версию программного средства не входят:

- автоматическое формирование заказов поставщикам;
- управление поставщиками;
- управление закупками;
- автоматическое управление складскими запасами;
- автоматическое изменение цен;
- финансовое планирование;
- полноценная ERP-функциональность;
- мобильное приложение;
- интеграция с внешними ERP- и CRM-системами;
- автоматическое получение данных из внешних торговых платформ;
- автоматическое принятие управленческих решений;
- распределённое обучение ML-модели;
- высоконагруженная кластерная инфраструктура;
- поддержка нескольких организаций в одном экземпляре системы;
- автоматическая синхронизация подразделений и должностей с внешней HR/ERP-системой;
- сложная иерархическая организационная структура с руководителями и подчинённостью.

Перечисленные возможности могут рассматриваться как направления дальнейшего развития, но не являются обязательными для сдачи текущего проекта.

## 12. Технологические ограничения

Проект является учебным, поэтому архитектурные решения должны соответствовать реальному объёму курсовой работы.

Необходимо избегать необоснованного усложнения системы.

В частности, не требуется:

- полноценная микросервисная архитектура;
- брокер сообщений без подтверждённой необходимости;
- Kubernetes;
- распределённая база данных;
- сложная облачная инфраструктура.

Использование одного внешнего объектного хранилища для фотографий профиля не рассматривается как построение сложной облачной инфраструктуры.

ML-сервис выделяется отдельно не ради построения микросервисной системы, а для изоляции Python/ML-части от Backend.

## 13. Ограничения исходных данных

Качество прогнозирования зависит от:

- полноты исторических данных;
- длины временного ряда;
- количества пропусков;
- наличия выбросов;
- структуры данных;
- стабильности закономерностей спроса.

Система не может гарантировать высокую точность прогнозирования для товара, если объём исторических данных недостаточен для работы выбранной модели.

## 14. Ограничения прогнозирования

Результат модели является прогнозом, а не гарантированным будущим значением спроса.

Качество результата может снижаться при:

- резких структурных изменениях спроса;
- появлении ранее отсутствовавших факторов;
- недостаточном количестве исторических наблюдений;
- существенном изменении поведения потребителей;
- наличии ошибок во входных данных.

Пользователь должен интерпретировать прогноз совместно с другой доступной информацией.

## 15. Критерии готовности системы

Система считается функционально готовой к сдаче, если выполняются следующие условия:

1. PostgreSQL разворачивается согласно инструкции.
2. Backend запускается и успешно подключается к базе данных.
3. ML-сервис запускается и предоставляет рабочие `/health` и `/predict`.
4. Frontend запускается и взаимодействует с Backend.
5. Пользователь может зарегистрироваться.
6. Пользователь может авторизоваться.
7. Заблокированный пользователь не может авторизоваться и использовать защищённые операции.
8. JWT используется для доступа к защищённым API.
9. Роли `USER` и `ADMIN` корректно учитываются при проверке доступа.
10. Пользователь может просматривать и изменять разрешённые личные данные профиля.
11. Пользователь может загрузить, заменить и удалить фотографию профиля.
12. Пользователь не может самостоятельно изменять должность, подразделение, роль и статус.
13. Администратор может просматривать пользователей и управлять их ролью, статусом и должностью.
14. Защищены собственная учётная запись администратора и последний активный администратор.
15. Администратор может управлять подразделениями.
16. Администратор может управлять должностями.
17. Каждая должность связана ровно с одним подразделением.
18. При назначении пользователю доступны только должности выбранного подразделения.
19. Деактивированные должности и подразделения сохраняются в существующих назначениях и не используются для новых.
20. Администратор может выполнять предусмотренные операции с товарами.
21. История продаж сохраняется в PostgreSQL.
22. Поддерживается импорт продаж из CSV.
23. Некорректный CSV обрабатывается предсказуемо и не повреждает сохранённые данные.
24. Пользователь может просматривать товары и историю продаж.
25. Пользователь может сформировать прогноз для выбранного товара.
26. Backend успешно взаимодействует с ML-сервисом.
27. Полученный прогноз сохраняется в PostgreSQL.
28. Пользователь может просмотреть результат прогнозирования.
29. Для результата отображаются предусмотренные метрики качества.
30. Пользователь может просматривать историю ранее выполненных прогнозов.
31. Основные ошибки обрабатываются без аварийного завершения системы.
32. Реализован и проверен механизм резервного копирования и восстановления PostgreSQL.
33. Критические компоненты покрыты предусмотренными тестами.
34. Выполнено комплексное тестирование пользовательского сценария.
35. README содержит достаточную информацию для запуска проекта.
36. В Git-репозитории отсутствуют секреты, временные файлы и локальные конфигурации, не предназначенные для публикации.

## 16. Итог

В рамках проекта разрабатывается законченная клиент-серверная система прогнозирования потребительского спроса с отдельным ML-компонентом и реляционной базой данных.

Функциональные границы ограничивают проект задачами управления товарами и историческими продажами, импорта исходных данных, формирования и анализа прогнозов, а также обеспечения необходимого уровня безопасности, надёжности и воспроизводимости.

Зафиксированный объём разработки является основой для формирования детальной спецификации требований.
