# Бизнес-процессы прогнозирования потребительского спроса

## 1. Назначение документа

Документ описывает процесс прогнозирования потребительского спроса до внедрения разрабатываемого программного средства в состоянии AS-IS и целевой процесс после его внедрения в состоянии TO-BE.

Анализ необходим для определения недостатков существующего подхода, выявления автоматизируемых операций и обоснования функций проектируемой системы.

В документе рассматриваются:

- процесс AS-IS;
- недостатки существующего процесса;
- процесс TO-BE;
- распределение действий между пользователем и программными компонентами;
- сравнение AS-IS и TO-BE.

Графические BPMN-модели хранятся отдельно в каталоге `docs/diagrams/bpmn`.

---

# 2. Процесс AS-IS

## 2.1. Общая характеристика

До внедрения специализированного программного средства прогнозирование потребительского спроса рассматривается как преимущественно ручной аналитический процесс.

Специалист получает исторические сведения о продажах из имеющихся источников, самостоятельно проверяет и подготавливает их, анализирует изменение спроса, выбирает способ прогнозирования и формирует результат.

Полученный прогноз затем используется как информационная основа для принятия управленческих решений.

## 2.2. Участники процесса AS-IS

В процессе выделяются следующие основные участники:

### Специалист

Выполняет:

- получение исторических данных;
- проверку данных;
- исправление обнаруженных проблем;
- подготовку данных;
- анализ динамики продаж;
- выбор метода прогнозирования;
- построение прогноза;
- оценку результата;
- подготовку итоговых материалов.

### Лицо, принимающее решение

Получает сформированный прогноз и использует его при планировании дальнейшей деятельности.

## 2.3. Входные данные

Для выполнения прогнозирования используются исторические данные о продажах.

Минимально необходимы:

- идентификатор товара;
- дата;
- количество проданных единиц.

В зависимости от доступного источника данные могут дополнительно содержать:

- наименование товара;
- категорию;
- цену;
- сведения о скидках;
- сведения об акциях;
- другие характеристики.

## 2.4. Последовательность процесса AS-IS

### Этап 1. Получение исторических данных

Специалист получает накопленные сведения о продажах из доступного источника.

Это могут быть:

- электронные таблицы;
- CSV-файлы;
- отчёты;
- данные учётной системы.

### Этап 2. Проверка данных

Специалист проверяет:

- наличие пропусков;
- корректность дат;
- корректность числовых значений;
- наличие дубликатов;
- полноту временного ряда;
- наличие аномальных наблюдений.

### Этап 3. Исправление проблем

При обнаружении ошибок специалист вручную корректирует или исключает проблемные записи.

После этого выполняется повторная проверка.

### Этап 4. Подготовка данных

Специалист выполняет необходимые преобразования:

- сортировку;
- фильтрацию;
- группировку;
- агрегирование;
- формирование временных рядов.

### Этап 5. Анализ спроса

Исследуются:

- динамика продаж;
- тренды;
- сезонные изменения;
- пики;
- провалы;
- аномальные значения.

### Этап 6. Выбор способа прогнозирования

Специалист выбирает доступный метод.

Это может быть:

- экспертная оценка;
- перенос последнего значения;
- скользящее среднее;
- статистический метод;
- иной доступный инструмент.

### Этап 7. Формирование прогноза

На основании выбранного метода рассчитываются предполагаемые значения будущего спроса.

### Этап 8. Оценка результата

Специалист анализирует сформированный прогноз.

Если результат кажется неудовлетворительным, специалист изменяет способ расчёта или параметры и повторяет прогнозирование.

### Этап 9. Подготовка результата

После получения приемлемого результата специалист формирует таблицу, график или отчёт.

### Этап 10. Передача результата

Результат передаётся лицу, принимающему решение.

# 3. Недостатки AS-IS

## 3.1. Высокая доля ручных операций

Значительная часть получения, проверки, подготовки и анализа данных выполняется вручную.

Это повышает трудоёмкость процесса.

## 3.2. Риск ошибок

Ручная обработка большого количества записей увеличивает вероятность:

- пропуска некорректных значений;
- ошибочного преобразования данных;
- неправильного применения формул;
- использования неактуальной версии набора данных.

## 3.3. Зависимость от специалиста

Результат зависит от:

- опыта пользователя;
- выбранного метода;
- способа интерпретации данных;
- правильности ручной подготовки.

## 3.4. Ограниченная масштабируемость

По мере увеличения:

- числа товаров;
- объёма истории;
- частоты прогнозирования

ручной процесс становится всё более трудоёмким.

## 3.5. Недостаточная воспроизводимость

Повторное получение идентичного результата затрудняется, если:

- не сохранены исходные данные;
- не зафиксированы параметры;
- неизвестен использованный метод;
- данные были изменены вручную.

## 3.6. Отсутствие централизованной истории

Результаты прогнозирования могут храниться в отдельных файлах и не иметь единого механизма:

- поиска;
- просмотра;
- сравнения;
- анализа предыдущих запусков.

## 3.7. Ограниченная оценка качества

При ручном подходе MAE, RMSE и MAPE могут не рассчитываться систематически.

Это затрудняет объективное сравнение используемых методов.

# 4. Процесс TO-BE

## 4.1. Общая характеристика

После внедрения программного средства значительная часть операций должна выполняться автоматически.

Пользователь взаимодействует с Frontend, Backend координирует бизнес-процесс и работу с PostgreSQL, а ML-сервис выполняет интеллектуальную часть прогнозирования.

Целевой процесс должен обеспечивать:

- централизованное хранение товаров;
- централизованное хранение продаж;
- импорт данных из CSV;
- автоматизированную проверку данных;
- получение исторических данных из PostgreSQL;
- вызов ML-сервиса;
- сохранение прогноза;
- визуализацию результата;
- ведение истории прогнозов.

---

# 5. Участники и компоненты TO-BE

## 5.1. Пользователь

Пользователь:

- авторизуется;
- выбирает товар;
- задаёт параметры прогнозирования;
- запускает процесс;
- анализирует результат;
- просматривает историю.

## 5.2. Администратор

Администратор дополнительно:

- управляет товарами;
- импортирует исторические продажи;
- получает отчёт о результатах импорта.

## 5.3. Frontend

Frontend:

- предоставляет пользовательский интерфейс;
- выполняет клиентскую проверку форм;
- передаёт запросы Backend;
- отображает состояние операций;
- отображает графики, метрики и ошибки.

## 5.4. Backend

Backend:

- проверяет пользователя и права доступа;
- проверяет параметры запросов;
- работает с PostgreSQL;
- получает историю продаж;
- взаимодействует с ML-сервисом;
- сохраняет прогнозы;
- предоставляет данные Frontend;
- преобразует технические ошибки в единый API-формат.

## 5.5. PostgreSQL

PostgreSQL хранит:

- пользователей;
- товары;
- исторические продажи;
- прогнозы;
- отдельные значения прогнозов;
- необходимые связанные данные.

## 5.6. ML-сервис

ML-сервис:

- принимает данные для прогнозирования;
- применяет предусмотренный preprocessing;
- загружает модель;
- выполняет inference;
- возвращает прогноз;
- предоставляет информацию о версии модели.

---

# 6. Последовательность процесса TO-BE

## Этап 1. Авторизация

Пользователь выполняет вход.

Backend проверяет учётные данные и предоставляет доступ к защищённым функциям после успешной авторизации.

## Этап 2. Подготовка исторических данных

До запуска прогнозирования в системе должны существовать:

- товар;
- достаточная история его продаж.

Исторические данные могут быть добавлены администратором посредством импорта CSV.

## Этап 3. Выбор товара

Пользователь открывает интерфейс прогнозирования и выбирает товар.

## Этап 4. Выбор горизонта

Пользователь указывает допустимый горизонт прогнозирования.

## Этап 5. Запуск

Frontend передаёт запрос Backend.

## Этап 6. Проверка параметров

Backend проверяет:

- авторизацию;
- существование товара;
- допустимость горизонта;
- наличие достаточной истории.

При обнаружении ошибки дальнейшее выполнение прекращается.

## Этап 7. Получение исторических продаж

Backend получает из PostgreSQL необходимые данные о продажах выбранного товара.

## Этап 8. Вызов ML-сервиса

Backend формирует запрос и передаёт данные ML-сервису.

## Этап 9. Предобработка

ML-сервис применяет тот же воспроизводимый pipeline подготовки данных, который предусмотрен для рабочего inference.

## Этап 10. Прогнозирование

Модель формирует значения спроса на указанный горизонт.

## Этап 11. Возврат результата

ML-сервис возвращает:

- прогнозные значения;
- версию модели;
- необходимые технические метаданные.

## Этап 12. Сохранение

Backend сохраняет:

- сведения о запуске;
- товар;
- пользователя;
- горизонт;
- версию модели;
- прогнозируемые значения;
- доступные показатели качества.

## Этап 13. Передача результата Frontend

Backend возвращает данные результата.

## Этап 14. Визуализация

Frontend отображает:

- исторические значения;
- прогноз;
- MAE, RMSE и MAPE при наличии;
- параметры запуска.

## Этап 15. Анализ

Пользователь анализирует полученный прогноз.

## Этап 16. История

Сформированный прогноз становится доступен в истории и может быть открыт повторно без выполнения нового inference.

---

# 7. Обработка отклонений TO-BE

## 7.1. Недостаточно исторических данных

Если истории недостаточно для модели:

1. Backend или ML-сервис обнаруживает проблему.
2. Прогноз не формируется.
3. Пользователь получает понятное сообщение.

## 7.2. ML-сервис недоступен

Если ML-сервис не отвечает:

1. Backend прекращает ожидание после установленного timeout.
2. Ошибка регистрируется.
3. Пользователь получает контролируемое сообщение.
4. Ранее сохранённые данные не повреждаются.

## 7.3. Ошибка модели

Если inference завершился ошибкой:

1. ML-сервис возвращает или регистрирует техническую ошибку.
2. Backend преобразует её в безопасную прикладную ошибку.
3. Неуспешный результат не сохраняется как успешно завершённый прогноз.

## 7.4. Ошибочный CSV

При импорте система должна:

- проверить структуру;
- проверить значения;
- определить ошибочные строки;
- сформировать отчёт;
- не допустить неконтролируемого повреждения данных.

# 8. Сравнение AS-IS и TO-BE

| Критерий | AS-IS | TO-BE |
| --- | --- | --- |
| Получение данных | Из разрозненных источников | Централизованное хранение в PostgreSQL |
| Подготовка данных | Преимущественно вручную | Автоматизированный pipeline |
| Проверка данных | Ручная | Формализованная валидация |
| Хранение товаров | Необязательно централизованное | В PostgreSQL |
| Хранение продаж | Файлы или внешние системы | В PostgreSQL |
| Массовая загрузка | Ручная работа с файлами | CSV-import |
| Выбор метода | Выполняется специалистом | Рабочая модель определена системой |
| Формирование прогноза | Ручной или полуавтоматический расчёт | ML-сервис |
| Использование LSTM | Не предусмотрено | Предусмотрено |
| Оценка качества | Может отсутствовать | MAE, RMSE, MAPE |
| История запусков | Разрозненные файлы | Централизованная история |
| Воспроизводимость | Ограниченная | Сохраняются параметры и версия модели |
| Визуализация | Формируется вручную | Формируется Frontend |
| Повторный просмотр | Требует поиска файлов | Через историю прогнозов |
| Контроль доступа | Не формализован | JWT и роли |
| Масштабирование на несколько товаров | Трудоёмко | Поддерживается системой |

---

# 9. Основной эффект автоматизации

Переход к TO-BE позволяет:

- сократить объём ручной подготовки;
- централизовать данные;
- стандартизировать процесс прогнозирования;
- снизить вероятность ошибок ручных вычислений;
- обеспечить сохранение истории;
- обеспечить единый расчёт метрик;
- сделать результат воспроизводимым;
- упростить повторный анализ;
- отделить процесс прогнозирования от внутренних деталей ML-модели.

При этом система остаётся инструментом поддержки принятия решений: итоговая интерпретация прогноза выполняется человеком.

# 11. Результат

Проведённое моделирование показывает переход от преимущественно ручного процесса прогнозирования к программно поддерживаемому процессу с централизованным хранением данных, формализованной проверкой, использованием ML-модели, сохранением прогнозов и визуальным анализом результатов.

Полученная модель TO-BE является основой для пользовательских сценариев и дальнейшего архитектурного проектирования.
