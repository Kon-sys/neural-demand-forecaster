# ML Dataset

## Назначение

Датасет используется для построения и оценки моделей прогнозирования
потребительского спроса по историческим данным продаж.

Основной временной ряд системы имеет вид:

`product_sku + date -> quantity`

Каждый `product_sku` соответствует отдельному ежедневному временному ряду
спроса.

В прикладной системе `product_sku` соответствует SKU товара.

Для внешних исследовательских наборов данных `product_sku` может
представлять составной идентификатор временного ряда, если этого требует
структура источника.

Например, для FreshRetailNet-50K используется комбинация:

`store_id + product_id`

которая преобразуется во внутренний идентификатор вида:

`STORE_<store_id>_PRODUCT_<product_id>`


## Источники данных

### Данные прикладной системы

Основным источником данных рабочей системы является таблица `sales`
PostgreSQL.

Связь продажи с товаром определяется через таблицу `products`:

`products.id -> sales.product_id`

Для ML используется стабильный предметный идентификатор товара `sku`,
а не внутренний идентификатор PostgreSQL.

Данные прикладной системы приводятся к контракту:

`product_sku,date,quantity`

### Синтетические данные

На ранних этапах разработки использовался воспроизводимый синтетический
датасет.

Он применяется для:

- разработки data pipeline;
- unit-тестирования;
- проверки preprocessing;
- проверки воспроизводимости;
- первичных ML-экспериментов.

Синтетические данные явно обозначаются как синтетические и не
интерпретируются как реальные рыночные наблюдения.

### M5 Forecasting

M5 Forecasting использовался как дополнительный внешний реальный набор
данных для проверки универсальности разработанного ML pipeline.

Данные M5 не используются как финальный экспериментальный набор
курсового проекта.

### FreshRetailNet-50K

Финальным экспериментальным набором данных для обучения и сравнения
моделей является FreshRetailNet-50K.

Исходные данные содержат ежедневные наблюдения для комбинаций:

`store_id + product_id`

Основными используемыми полями являются:

- `store_id`;
- `product_id`;
- `dt`;
- `sale_amount`.

Они преобразуются в ML contract следующим образом:

`store_id + product_id -> product_sku`

`dt -> date`

`sale_amount -> quantity`

Поле `sale_amount` является вещественной величиной, поэтому ML contract
поддерживает не только целые, но и дробные значения целевой переменной.

Для финального эксперимента используется 300 store-product временных
рядов.

Выбор временных рядов выполняется только по TRAIN-части данных без
использования будущего EVAL-периода.


## Raw dataset

Базовый raw contract содержит обязательные поля:

| Поле | Тип | Назначение |
| --- | --- | --- |
| `product_sku` | string | стабильный идентификатор временного ряда |
| `date` | date | календарная дата |
| `quantity` | numeric | неотрицательная величина спроса или объёма продаж |

Ограничения:

- `product_sku` не может быть пустым;
- `date` должна быть корректной календарной датой;
- `quantity` должна быть числовым значением;
- `quantity` должна быть конечным значением;
- `quantity >= 0`;
- комбинация `product_sku + date` должна быть уникальной.

`quantity` может содержать как целые, так и дробные значения.

Это необходимо для поддержки внешних наборов данных, в которых величина
спроса представлена нормализованным или вещественным показателем продаж.

Raw datasets хранятся локально в:

`datasets/raw/`

и не коммитятся в Git.


## Processed dataset

Processed dataset имеет поля:

| Поле | Тип | Назначение |
| --- | --- | --- |
| `product_sku` | string | идентификатор временного ряда |
| `date` | date | календарная дата |
| `quantity` | float64 | величина спроса за день |
| `is_imputed` | boolean | признак восстановленной календарной даты |

Для каждого временного ряда строится непрерывный ежедневный календарь
от первой до последней наблюдаемой даты этого ряда.

Если календарная дата отсутствует внутри наблюдаемого интервала,
создаётся строка:

`quantity = 0.0`

`is_imputed = True`

Исходные наблюдения получают:

`is_imputed = False`

Даты до первого наблюдения временного ряда и после последнего наблюдения
искусственно не создаются.

Processed datasets хранятся локально в:

`datasets/processed/`

и не коммитятся в Git.


## Проверка качества данных

Перед использованием dataset выполняются следующие проверки:

- наличие обязательных колонок;
- отсутствие null в обязательных полях;
- корректность календарных дат;
- числовой тип `quantity`;
- отсутствие `NaN` и бесконечных значений `quantity`;
- отсутствие отрицательной величины спроса;
- отсутствие дубликатов `product_sku + date`;
- хронологический порядок наблюдений;
- непрерывность ежедневного календаря;
- корректность `is_imputed`;
- значение `quantity = 0` для восстановленных строк.

Дробные значения `quantity` считаются допустимыми.


## Обработка отсутствующих дат

Для каждого временного ряда определяется его наблюдаемый временной
интервал.

Если внутри этого интервала отсутствует календарная дата, она
восстанавливается как:

`quantity = 0.0`

`is_imputed = True`

Такая операция выполняется только внутри фактического временного
интервала ряда.

До первой известной даты и после последней известной даты дополнительные
наблюдения не создаются.


## Идентификатор временного ряда

Внутренний ML pipeline работает с абстрактным идентификатором:

`product_sku`

Его конкретное формирование зависит от источника данных.

Для прикладной системы:

`product_sku = products.sku`

Для FreshRetailNet-50K:

`product_sku = STORE_<store_id>_PRODUCT_<product_id>`

Это позволяет использовать один и тот же preprocessing и forecasting
pipeline для разных источников данных.


## Train / Validation / Test

Для временных рядов случайное перемешивание до разделения не
используется.

Разделение выполняется исключительно хронологически:

`TRAIN -> VALIDATION -> TEST`

TRAIN содержит наиболее ранний временной интервал и используется для:

- обучения модели;
- определения параметров preprocessing;
- определения параметров нормализации.

VALIDATION следует после TRAIN и используется для:

- выбора конфигурации модели;
- выбора гиперпараметров;
- контроля переобучения;
- выбора baseline-конфигурации.

TEST содержит наиболее поздний временной интервал и используется только
для итоговой оценки уже зафиксированных моделей.

Будущие наблюдения не используются для подготовки или настройки моделей.


## Финальный split FreshRetailNet-50K

Исходный TRAIN FreshRetailNet-50K содержит данные:

`2024-03-28 -> 2024-06-25`

Официальный EVAL-период содержит:

`2024-06-26 -> 2024-07-02`

В курсовом проекте используется следующий split.

### TRAIN

`2024-03-28 -> 2024-06-11`

Продолжительность:

`76 дней`

### VALIDATION

`2024-06-12 -> 2024-06-25`

Продолжительность:

`14 дней`

### TEST

`2024-06-26 -> 2024-07-02`

Продолжительность:

`7 дней`

TEST соответствует исходному EVAL-периоду FreshRetailNet-50K.

Он не используется при выборе baseline или настройке LSTM и
резервируется для итогового сравнения моделей.


## Финальная выборка FreshRetailNet-50K

Исходный набор содержит:

- 4 500 000 TRAIN-наблюдений;
- 350 000 EVAL-наблюдений;
- 50 000 store-product временных рядов.

Для курсового проекта детерминированно выбирается:

`300 временных рядов`

Выбор выполняется только на TRAIN.

Для повышения разнообразия используется балансировка по
`first_category_id`.

В итоговой выборке представлены:

`32 категории первого уровня`

При ранжировании временных рядов внутри категории учитываются:

1. количество дней с ненулевым спросом;
2. суммарная величина продаж;
3. `store_id`;
4. `product_id`.

Итоговый processed dataset содержит:

`300 × 97 = 29 100 наблюдений`

Диапазон:

`2024-03-28 -> 2024-07-02`


## Data Leakage

Для предотвращения утечки будущих данных соблюдаются следующие правила:

1. временные ряды для экспериментальной выборки выбираются только по
   TRAIN;
2. разделение выполняется хронологически;
3. случайное перемешивание временных рядов во времени не используется;
4. параметры нормализации определяются только по TRAIN;
5. VALIDATION не используется для обучения финальной модели;
6. TEST не используется при выборе параметров;
7. прогноз для даты `t` формируется только из наблюдений,
   предшествующих дате `t`.


## Текущее состояние данных Backend

Текущая локальная PostgreSQL содержит только небольшой тестовый набор
данных прикладной системы:

- 4 исходных наблюдения;
- 1 товар;
- период от `2026-01-01` до `2026-02-01`;
- 28 отсутствующих календарных дней внутри наблюдаемого интервала.

После восстановления ежедневного календаря получается 32 строки,
из которых 28 являются восстановленными.

Этот набор используется только для проверки интеграции:

`Backend -> ML data pipeline`

Он недостаточен для полноценного обучения и сравнительной оценки
моделей.


## Назначение разных наборов данных

В проекте используются несколько источников с различным назначением:

| Dataset | Назначение |
| --- | --- |
| Backend test sales | проверка интеграции Backend и ML |
| Synthetic dataset | разработка, тестирование и воспроизводимость pipeline |
| M5 Forecasting | дополнительная проверка pipeline на реальных данных |
| FreshRetailNet-50K | финальное обучение и сравнение ML-моделей |

Таким образом, разработка ML pipeline не зависит от одного конкретного
набора данных, а финальные экспериментальные результаты формируются на
FreshRetailNet-50K.
