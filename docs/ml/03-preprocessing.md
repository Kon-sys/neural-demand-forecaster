# ML Preprocessing

## 1. Назначение

Этап preprocessing подготавливает временной ряд спроса к последующему
обучению baseline- и LSTM-моделей.

Preprocessing должен быть воспроизводимым и не допускать использования
информации из будущих наблюдений при подготовке обучающих данных.

## 2. Уже реализованные операции

Часть операций подготовки была реализована на этапе формирования
ML Dataset.

К ним относятся:

- проверка структуры данных;
- проверка обязательных значений;
- проверка корректности дат;
- проверка `quantity`;
- запрет отрицательных значений;
- обработка отсутствующих календарных дат;
- обнаружение дубликатов `product_sku + date`;
- сортировка наблюдений по времени;
- формирование непрерывного ежедневного ряда;
- хронологическое разделение train / validation / test.

Повторная реализация этих операций в отдельном preprocessing pipeline
не выполняется.

## 3. Агрегирование по датам

Прикладная модель данных Demand Forecast уже использует гранулярность:

`один товар -> одна календарная дата -> одно агрегированное значение`

В PostgreSQL комбинация товара и даты является уникальной.

Поэтому данные, поступающие из основной системы, не требуют повторного
суммирования нескольких записей одной даты внутри ML pipeline.

Если в дальнейшем будет подключён источник транзакционного уровня,
агрегирование должно выполняться до приведения данных к текущему
ML data contract.

## 4. Обработка аномалий

Структурно некорректные значения обрабатываются как ошибки данных.

Например:

- отрицательный `quantity`;
- некорректная дата;
- отсутствующий идентификатор товара.

Для статистически необычных, но допустимых положительных значений
используется отдельное обнаружение аномалий.

В текущей реализации применяется IQR-анализ отдельно для каждого товара.

Границы определяются как:

`lower = Q1 - 1.5 * IQR`

`upper = Q3 + 1.5 * IQR`

Нижняя граница дополнительно ограничивается нулём.

Статистическая аномалия автоматически не удаляется и не заменяется.

Такой подход выбран потому, что резкое увеличение или уменьшение
фактического спроса может являться реальным бизнес-событием, а не
ошибкой исходных данных.

## 5. Нормализация

Для подготовки значений к использованию нейросетевой моделью
реализовано Min-Max масштабирование.

Используется преобразование:

`x_scaled = (x - min_train) / (max_train - min_train)`

Критически важно, что `min` и `max` определяются исключительно
по обучающей выборке.

Validation и test преобразуются параметрами, полученными из train.

Таким образом данные будущих периодов не влияют на параметры
предобработки.

Значения validation или test могут выходить за диапазон `[0; 1]`,
если фактический спрос выходит за диапазон, наблюдавшийся в train.
Это не считается ошибкой.

Для получения прогнозов в исходных единицах реализовано обратное
преобразование.

Параметры scaler могут сохраняться в JSON и повторно загружаться.
Это необходимо для последующего использования того же preprocessing
во время inference в ML-сервисе.

## 6. Формирование временного окна

Для LSTM реализован универсальный механизм формирования supervised
последовательностей.

При размере окна `N`:

`[y(t-N), ..., y(t-1)] -> y(t)`

Целевое значение никогда не входит в собственное входное окно.

Конкретный размер окна не фиксируется на этапе preprocessing.

Он является параметром и будет определён при разработке и настройке
LSTM.

## 7. Train / validation / test

Временные данные разделяются исключительно хронологически:

`TRAIN -> VALIDATION -> TEST`

Перемешивание до разделения не применяется.

TRAIN используется для:

- обучения модели;
- определения параметров scaler.

VALIDATION используется для:

- настройки модели;
- выбора гиперпараметров;
- контроля переобучения.

TEST резервируется для итоговой оценки.

## 8. Исключение утечки будущего

Для предотвращения data leakage выполняются следующие правила:

1. разделение выполняется по времени;
2. scaler обучается только на TRAIN;
3. validation и test не участвуют в расчёте параметров scaler;
4. входное окно содержит только наблюдения, предшествующие target;
5. test не используется для настройки модели.

## 9. Повторное использование preprocessing

Одинаковые правила preprocessing должны применяться:

- при обучении;
- при validation;
- при test;
- при последующем inference.

Сохранённые параметры scaler являются частью ML-артефактов итоговой
модели.

Это обеспечивает воспроизводимость преобразований между этапом
исследования и рабочим ML-сервисом.

## 10. Результат

После завершения preprocessing проект располагает механизмами:

- выявления статистических аномалий;
- Min-Max нормализации;
- обратного преобразования;
- сохранения и загрузки scaler;
- формирования временных окон произвольной длины;
- подготовки train / validation / test без утечки будущего.

Полученная инфраструктура является основой для разработки baseline
и нейросетевой модели LSTM.
