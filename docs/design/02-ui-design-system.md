# UI Design System

## 1. Назначение

Документ определяет базовые правила визуального оформления пользовательского интерфейса программного средства прогнозирования потребительского спроса.

Design System должна обеспечить:

- визуальную целостность;
- предсказуемое поведение компонентов;
- читаемость аналитических данных;
- повторное использование UI-компонентов;
- согласованность пользовательских и административных страниц;
- возможность последующей реализации Frontend без изменения визуальной концепции.

Основная визуальная концепция:

    FORECAST SIGNAL

---

# 2. Характер интерфейса

Интерфейс воспринимается как современный аналитический продукт.

Основные характеристики:

- минималистичный;
- профессиональный;
- технологичный;
- ориентированный на данные;
- контрастный;
- без визуального шума;
- с умеренным использованием motion;
- с выраженной иерархией навигации и рабочего пространства.

Основной принцип:

    compact dark shell
        +
    bright analytical workspace

Главный акцент делается на:

- таблицах;
- графиках;
- числовых показателях;
- формах;
- статусах;
- действиях пользователя.

---

# 3. Layout

Desktop-интерфейс строится вокруг:

- Sidebar;
- Header;
- Content Area.

Sidebar визуально отделяется от светлого рабочего пространства.

Content Area должна предоставлять достаточную ширину для:

- таблиц;
- графиков;
- Dashboard;
- административных страниц;
- форм.

Переход между пользовательскими и административными страницами не должен визуально менять дизайн-систему.

---

# 4. Сетка

Основной принцип:

    8 px grid

Типовые значения:

    4 px
    8 px
    12 px
    16 px
    24 px
    32 px
    40 px
    48 px

Произвольных значений отступов следует избегать.

---

# 5. Контейнер страницы

Типовой page padding Desktop:

    24–32 px

Страница должна использовать доступную ширину рационально.

Текстовые блоки не растягиваются чрезмерно.

Таблицы, графики и административные списки могут использовать более широкую область.

---

# 6. Типографика

Основной интерфейсный шрифт:

    IBM Plex Sans

Для технических данных, кодов, небольших цифровых или signal-элементов может использоваться:

    IBM Plex Mono

Основные уровни:

## Page Title

Название страницы.

## Section Title

Название функционального блока.

## Body

Основной интерфейсный текст.

## Secondary

Дополнительная информация.

## Caption

Подписи и метаданные.

## Mono / Technical

Используется ограниченно для:

- SKU;
- model version;
- некоторых числовых сигналов;
- технических идентификаторов.

Typography не должна превращать интерфейс в developer console.

---

# 7. Цветовая концепция

Цвета определяются через semantic tokens.

Основные визуальные группы:

    shell
    background
    surface
    surface-secondary
    border

    text-primary
    text-secondary
    text-disabled

    primary
    primary-hover
    primary-active

    signal
    success
    warning
    error
    info

В концепции используются:

- charcoal / near-black — оболочка и навигация;
- светлое нейтральное рабочее пространство;
- cobalt — основной интерактивный цвет;
- cyan — signal / analytical accent.

Точные значения должны храниться централизованно в CSS variables / design tokens.

Компоненты не должны содержать случайные самостоятельные цвета.

---

# 8. Контраст

Текст и интерактивные элементы должны иметь достаточный контраст.

Secondary text остаётся читаемым.

Цвет не является единственным способом передачи:

- ошибки;
- блокировки;
- статуса;
- выбранного состояния.

Для статуса дополнительно используются:

- текст;
- icon;
- badge;
- label.

---

# 9. Border Radius

Используется единая система скруглений.

Уровни:

    small
    medium
    large

Ориентировочно:

    small  = 6 px
    medium = 10 px
    large  = 14 px

Фактические значения должны совпадать с токенами реализованного прототипа.

---

# 10. Тени и глубина

Тени используются умеренно.

Допустимы для:

- dropdown;
- overlay;
- modal;
- floating menu;
- floating signal element.

Основные поверхности разделяются преимущественно через:

- фон;
- border;
- spacing;
- тональный контраст.

Сильная тень не используется как единственный способ отделения карточки.

---

# 11. Motion

Motion используется для улучшения восприятия состояния, а не как декоративный эффект.

Подходящие сценарии:

- page transition;
- появление overlay;
- hover;
- раскрытие menu;
- состояние Forecast Processing;
- изменение аналитического signal;
- смена tab.

Motion должен быть:

- быстрым;
- спокойным;
- предсказуемым;
- не мешающим работе с таблицами.

---

# 12. Кнопки

Основные варианты:

- Primary;
- Secondary;
- Ghost;
- Danger.

## Primary

Главное действие области.

Примеры:

- Войти;
- Создать товар;
- Импортировать;
- Построить прогноз;
- Сохранить;
- Добавить подразделение;
- Добавить должность.

На одной локальной области не должно быть нескольких конкурирующих Primary-кнопок.

## Secondary

Используется для альтернативного действия.

## Ghost

Для второстепенных действий и compact toolbar.

## Danger

Используется для потенциально разрушительных действий:

- удалить;
- заблокировать;
- деактивировать.

---

# 13. Состояния кнопок

Каждая кнопка предусматривает:

- default;
- hover;
- active;
- focus;
- disabled;
- loading.

Loading предотвращает повторную отправку.

Disabled не должен использоваться вместо объяснения бизнес-ограничения там, где пользователь должен понимать причину.

---

# 14. Поля ввода

Компоненты:

- Text Input;
- Password Input;
- Search Input;
- Select;
- Number Input;
- Date Picker;
- File Upload.

Поле содержит:

- label;
- value;
- placeholder при необходимости;
- helper text;
- error;
- focus state;
- disabled/read-only state при необходимости.

Label не заменяется только placeholder.

---

# 15. Read-only организационные поля

В Profile поля:

- Подразделение;
- Должность;
- Роль;

не должны выглядеть как случайно отключённые input.

Используется специальное информационное представление.

Пример:

    Подразделение
    Отдел разработки
    Назначается администратором

Допускается:

- lock icon;
- muted background;
- secondary helper text.

---

# 16. Select

Select используется для:

- товара;
- роли;
- статуса;
- подразделения;
- должности.

Select должен поддерживать:

- keyboard focus;
- выбранное значение;
- пустое значение;
- disabled option при необходимости;
- длинные подписи;
- состояние ошибки.

---

# 17. Зависимые Select Department → Position

При редактировании пользователя используются связанные поля:

    Department
        ↓
    Position

После выбора Department список Position фильтруется.

Показываются активные должности выбранного подразделения.

Если текущая Position пользователя деактивирована, она может оставаться видимой как существующее значение.

При смене Department несовместимая Position очищается.

UI не должен позволять сохранить визуально противоречивую комбинацию.

---

# 18. Формы

Формы имеют:

- логичную последовательность;
- понятные label;
- единое расположение ошибок;
- предсказуемое расположение действий;
- явное состояние сохранения.

Создание и редактирование одной сущности должны использовать одинаковую структуру.

---

# 19. Avatar

Компонент Avatar используется:

- в Sidebar/Header;
- в Profile;
- в Users Management.

Состояния:

- фотография;
- fallback initials;
- loading;
- preview;
- error.

Profile предоставляет действия:

- Загрузить фото;
- Заменить фото;
- Удалить фото.

Avatar в таблице Users не должен занимать чрезмерное пространство.

---

# 20. File Upload

File Upload используется:

- для CSV;
- для avatar.

Тип операции должен быть визуально понятен.

Для avatar:

- JPEG;
- PNG;
- WebP;
- до 5 MB.

Ошибка файла показывается рядом с контролом.

---

# 21. Таблицы

Таблицы являются одним из основных компонентов системы.

Поддерживаются:

- header;
- rows;
- hover;
- loading;
- empty;
- error;
- pagination;
- row actions;
- responsive overflow.

Числовые значения выравниваются для удобного сравнения.

---

# 22. Users Table

Таблица пользователей может содержать:

- avatar;
- имя;
- email;
- подразделение;
- должность;
- роль;
- статус;
- действия.

При малой ширине допускается:

- горизонтальный scroll;
- переход к компактному card/list pattern.

Статус `BLOCKED` должен считываться не только по цвету.

---

# 23. Organization Table

Подразделения:

- название;
- статус;
- действия.

Должности:

- название;
- подразделение;
- статус;
- действия.

Неактивные элементы визуально ослабляются, но остаются читаемыми.

---

# 24. Карточки

Используются для:

- Dashboard KPI;
- MAE;
- RMSE;
- MAPE;
- кратких аналитических показателей.

Карточка не должна превращаться в контейнер для большого количества разнородной информации.

---

# 25. График прогнозирования

График различает:

- историю;
- прогноз;
- фактические значения будущего периода при наличии.

Требования:

- читаемая временная ось;
- legend;
- tooltip;
- единицы измерения;
- адаптивное количество подписей.

Нельзя полагаться только на малое различие оттенков.

---

# 26. Status Badge

Используется для коротких состояний.

Forecast:

    COMPLETED
    FAILED
    PROCESSING
    PENDING

User:

    ACTIVE
    BLOCKED

Reference data:

    ACTIVE
    INACTIVE

В пользовательском интерфейсе используются локализованные подписи.

Например:

    Активен
    Заблокирован
    Активно
    Неактивно

---

# 27. Role Badge

Для роли пользователя допускается компактный badge:

    USER
    ADMIN

Role Badge не должен конкурировать с Account Status Badge.

Роль и статус — разные понятия и не объединяются в один индикатор.

---

# 28. Tabs

Tabs используются на странице:

    Оргструктура

Вкладки:

    Подразделения
    Должности

Tabs должны иметь:

- явное active state;
- keyboard focus;
- достаточную clickable area.

Не рекомендуется использовать tabs для основных верхнеуровневых разделов приложения.

---

# 29. Toast

Toast используется для краткого результата операции.

Примеры:

- Товар создан;
- Профиль обновлён;
- Фото профиля обновлено;
- Пользователь изменён;
- Подразделение создано;
- Должность изменена;
- Импорт завершён.

Критическая информация не должна существовать только в Toast.

---

# 30. Overlay / Modal

Overlay используется для коротких действий:

- подтверждение;
- редактирование пользователя;
- создание подразделения;
- редактирование подразделения;
- создание должности;
- редактирование должности.

Сложные многошаговые процессы размещаются на отдельной странице.

Overlay должен:

- помещаться во viewport;
- поддерживать keyboard focus;
- иметь явное действие закрытия;
- не терять введённые данные неожиданно.

---

# 31. Confirmation Dialog

Используется для:

- удаления товара;
- блокировки пользователя;
- деактивации подразделения;
- деактивации должности.

Текст должен сообщать конкретное действие.

Например:

    Заблокировать пользователя?

а не:

    Вы уверены?

---

# 32. Skeleton и Loading

Skeleton подходит для:

- таблиц;
- Dashboard;
- Profile;
- аналитических карточек.

Spinner / progress подходит для:

- отправки формы;
- CSV import;
- avatar upload;
- Forecast Processing.

Loading визуально связывается с выполняемой операцией.

---

# 33. Empty State

Содержит:

- объяснение;
- дополнительный текст;
- CTA при необходимости.

Примеры:

    Подразделения пока не созданы.

    [Добавить подразделение]

или:

    Прогнозы ещё не создавались.

    [Создать прогноз]

---

# 34. Error State

Page Error State содержит:

- заголовок;
- понятное описание;
- действие восстановления.

Пример:

    Не удалось загрузить пользователей.

    Проверьте соединение и попробуйте снова.

    [Повторить]

---

# 35. Inline Validation

Используется для:

- email;
- обязательного названия;
- duplicate Department;
- duplicate Position;
- отсутствующего Department для Position;
- некорректного файла.

Ошибки отображаются рядом с соответствующим полем.

---

# 36. Иконки

Иконки используются как дополнительное средство распознавания.

Они не заменяют текст, если действие неоднозначно.

Особенно:

- удаление;
- блокировка;
- CSV import;
- Forecast;
- Organization;
- avatar upload.

Иконки Sidebar должны использовать единый визуальный стиль.

---

# 37. Sidebar

USER:

    Главная
    Товары
    Продажи
    Прогнозирование
    История прогнозов

ADMIN дополнительно:

    Импорт CSV
    Пользователи
    Оргструктура

Profile доступен через account/avatar block.

Sidebar должен:

- показывать active route;
- поддерживать collapse;
- скрывать ADMIN routes от USER.

---

# 38. Header

Header содержит:

- page context;
- user;
- role;
- avatar;
- account menu;
- logout.

Header не дублирует всю Sidebar-навигацию.

---

# 39. Profile UI

Profile состоит из:

- identity area;
- avatar;
- personal data form;
- organizational information.

Personal data:

- name;
- email.

Organizational:

- department;
- position;
- role.

Организационные поля visually read-only.

---

# 40. User Management UI

Страница администратора строится вокруг:

- search;
- users table;
- status badges;
- edit action.

Редактирование:

    Department Select
    Position Select
    Role Select
    Status Select

Имя, email и avatar не изменяются через административную форму.

---

# 41. Organization UI

Страница содержит:

    Tabs
      ├── Departments
      └── Positions

Основное действие зависит от tab:

    Добавить подразделение

или:

    Добавить должность

Не используется отдельный Sidebar item для каждого справочника.

---

# 42. Опасные административные ограничения

Интерфейс должен понятно отображать Backend-отказы:

- self-block;
- self-demotion;
- last active admin;
- перенос назначенной Position;
- назначение inactive Position;
- назначение Position inactive Department.

Такие ситуации не должны выглядеть как техническая ошибка неизвестного типа.

---

# 43. Responsive behaviour

Целевой формат:

    Desktop / Laptop

При уменьшении ширины:

- Sidebar сворачивается;
- таблицы получают scroll;
- формы становятся одноколоночными;
- cards перестраиваются;
- graph адаптируется;
- overlay ограничивается viewport.

Критические функции не скрываются.

---

# 44. Accessibility

Минимальные требования:

- visible focus;
- label;
- keyboard navigation;
- достаточный contrast;
- понятные ошибки;
- semantic controls;
- accessible buttons;
- status не только цветом.

---

---

# 46. Ограничения Design System

В MVP не требуется:

- сложная theme system;
- пользовательский конструктор layout;
- отдельный UI-framework поверх используемой библиотеки;
- сложная визуализация оргструктуры;
- tree editor Department;
- отдельная дизайн-система для ADMIN.

USER и ADMIN используют одну визуальную систему.

---

# 47. Результат

Design System фиксирует правила построения интерфейса и формирует основу для:

- визуальной целостности;
- UI-kit;
- реализации React-компонентов;
- Profile;
- Users Management;
- Organization;
- Forecast UI;
- адаптивного поведения;
- единообразия пользовательских и административных страниц.

Интерфейс должен сохранять концепцию `FORECAST SIGNAL` на всех экранах приложения.
