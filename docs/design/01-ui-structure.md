# Структура пользовательского интерфейса

## 1. Назначение документа

Документ определяет структуру пользовательского интерфейса программного средства прогнозирования потребительского спроса.

Спецификация сформирована на основании:

- функциональных требований;
- нефункциональных требований;
- пользовательских сценариев;
- архитектуры системы;
- REST API;
- разработанного интерактивного UI-прототипа.

Документ фиксирует:

- состав экранов;
- назначение экранов;
- навигацию;
- доступность функций по ролям;
- структуру профиля пользователя;
- административное управление пользователями;
- управление подразделениями и должностями;
- состав основных элементов интерфейса;
- состояния загрузки;
- пустые состояния;
- состояния ошибок;
- пользовательский поток формирования прогноза.

---

# 2. Общая концепция интерфейса

Интерфейс представляет собой настольное web-приложение аналитического типа.

Основная визуальная концепция:

`FORECAST SIGNAL`.

Интерфейс сочетает:

- компактную тёмную навигационную оболочку;
- светлое рабочее пространство;
- выраженный акцент на аналитических данных;
- лаконичную типографику;
- небольшое количество акцентных цветов;
- чёткое разделение пользовательских и административных сценариев.

Основные приоритеты:

- высокая читаемость;
- минимальное количество действий для выполнения основных сценариев;
- акцент на данных и прогнозах;
- единообразная навигация;
- отсутствие визуальной перегруженности;
- понятная обратная связь;
- отчётливое разделение прав `USER` и `ADMIN`;
- согласованность интерфейса с фактическими ограничениями Backend.

Основным рабочим пространством является Desktop-интерфейс.

При уменьшении ширины окна структура должна адаптироваться без потери основных функций.

---

# 3. Роли и интерфейс

Система поддерживает две роли:

- `USER`;
- `ADMIN`.

Дополнительно каждая учётная запись имеет статус:

- `ACTIVE`;
- `BLOCKED`.

Статус используется Backend для определения доступности учётной записи.

## 3.1. USER

Пользователю доступны:

- Dashboard;
- Товары;
- Продажи;
- Прогнозирование;
- История прогнозов;
- собственный профиль.

Пользователь может:

- просматривать товары;
- просматривать продажи;
- фильтровать данные;
- создавать прогноз;
- анализировать результат;
- просматривать историю прогнозов;
- просматривать собственный профиль;
- изменять имя;
- изменять email;
- загружать фотографию профиля;
- заменять фотографию профиля;
- удалять фотографию профиля;
- просматривать назначенную должность;
- просматривать подразделение;
- просматривать собственную роль.

Пользователь не может самостоятельно изменять:

- должность;
- подразделение;
- роль;
- статус.

## 3.2. ADMIN

Администратору доступны все функции `USER`.

Дополнительно он получает:

- создание товара;
- редактирование товара;
- удаление товара;
- импорт продаж из CSV;
- просмотр пользователей;
- изменение роли пользователя;
- изменение статуса пользователя;
- назначение должности пользователю;
- управление подразделениями;
- управление должностями;
- управление принадлежностью должности подразделению.

Административные действия не должны отображаться пользователю `USER` как активные доступные функции.

Скрытие элемента во Frontend не заменяет проверку прав на Backend.

# 6. Страница Login

Маршрут:

    /login

## Назначение

Авторизация зарегистрированного пользователя.

## Основные элементы

### Заголовок

Название программного средства и краткое пояснение назначения.

### Форма

Поля:

- Email;
- Пароль.

Действия:

- Войти;
- Перейти к регистрации.

## Валидация

Frontend проверяет:

- заполненность email;
- корректность формата email;
- заполненность пароля.

Backend выполняет окончательную проверку.

## Состояние отправки

Во время запроса:

- кнопка входа блокируется;
- отображается индикатор загрузки;
- повторная отправка предотвращается.

## Ошибка учётных данных

При неверных данных отображается понятное сообщение:

    Неверный email или пароль.

## Заблокированная учётная запись

Если Backend возвращает состояние `BLOCKED`, пользователь получает отдельное сообщение о недоступности учётной записи.

JWT для заблокированной учётной записи не должен выдаваться.

Технические Backend-ошибки пользователю напрямую не показываются.

# 7. Страница Registration

Маршрут:

    /register

## Назначение

Создание учётной записи пользователя.

Новая учётная запись получает:

    role = USER
    status = ACTIVE

## Поля

- Имя;
- Email;
- Пароль;
- Подтверждение пароля.

На регистрации не выбираются:

- роль;
- статус;
- подразделение;
- должность.

После регистрации пользователь может не иметь назначенной должности.

## Действия

- Зарегистрироваться;
- Вернуться к входу.

## Проверки

Frontend проверяет:

- заполненность;
- формат email;
- совпадение паролей;
- минимальные требования к паролю.

Backend выполняет окончательную проверку.

## Успешный результат

После успешной регистрации пользователь получает уведомление и может перейти к авторизации.

# 9. Sidebar

Sidebar обеспечивает доступ к основным разделам приложения.

## 9.1. Навигация USER

Пользователь видит:

    Главная
    Товары
    Продажи
    Прогнозирование
    История прогнозов

Профиль доступен через блок пользователя / avatar в Sidebar или Header.

Отдельный постоянный пункт `Профиль` необязателен, если переход через пользовательский блок визуально очевиден.

## 9.2. Навигация ADMIN

Администратор дополнительно видит:

    Импорт CSV
    Пользователи
    Оргструктура

Пункты:

    Пользователи
    Оргструктура

являются административными.

При наличии места они могут быть визуально объединены в группу:

    Управление

## 9.3. Состояние активного пункта

Текущий раздел должен быть визуально однозначно выделен.

Sidebar не должен содержать элементы, к которым текущий пользователь не имеет доступа.

---

# 10. Header

Header содержит только глобально полезные элементы.

Основные элементы:

- название текущей страницы;
- при необходимости breadcrumb;
- данные текущего пользователя;
- роль;
- avatar;
- меню аккаунта;
- выход.

Переход в профиль должен быть доступен через avatar или пользовательский блок.

Header не должен становиться второй основной панелью навигации.

# 11. Dashboard

Маршрут:

    /dashboard

Допускается перенаправление:

    / -> /dashboard

## Назначение

Предоставить краткое представление о состоянии данных и быстрый доступ к основным операциям.

Dashboard не должен быть визуально перегруженным.

## Основные блоки

### Статистические показатели

Могут отображаться:

- количество товаров;
- количество записей продаж;
- количество выполненных прогнозов;
- дата последнего прогноза.

### Основное действие

Выделенная кнопка:

    Создать прогноз

### Последние прогнозы

Для каждого запуска:

- товар;
- дата;
- горизонт;
- статус.

### Быстрые действия USER

- создать прогноз;
- посмотреть продажи;
- открыть историю прогнозов.

### Быстрые действия ADMIN

Дополнительно:

- импортировать CSV;
- добавить товар;
- открыть управление пользователями.

# 12. Profile

Маршрут:

    /profile

## Назначение

Просмотр и изменение собственного профиля.

Страница одинакова по общей структуре для `USER` и `ADMIN`.

Администратор также изменяет собственные персональные данные через Profile, а не через Users Management.

## Основная информация

Отображаются:

- фотография;
- имя;
- email;
- подразделение;
- должность;
- роль;
- статус учётной записи.

## Редактируемые поля

Пользователь может изменять:

- имя;
- email.

## Нередактируемые организационные поля

Пользователь не может самостоятельно изменять:

- подразделение;
- должность;
- роль;
- статус.

Подразделение и должность должны отображаться как информационные read-only поля.

Не рекомендуется использовать обычные disabled input, создающие впечатление неработающей формы.

Предпочтительная структура:

    Подразделение
    Отдел разработки

    Назначается администратором

и:

    Должность
    Senior Developer

    Назначается администратором

Допускается использование:

- lock icon;
- secondary surface;
- helper text.

Если должность не назначена:

    Не назначено

# 13. Avatar пользователя

Profile должен поддерживать:

- загрузку фотографии;
- preview;
- замену фотографии;
- удаление фотографии.

## Поддерживаемые форматы

- JPEG;
- PNG;
- WebP.

## Ограничение размера

Для MVP:

    до 5 MB

## Состояния

Необходимо предусмотреть:

- отсутствие фотографии;
- preview выбранного файла;
- загрузку;
- ошибку формата;
- ошибку размера;
- ошибку Backend / Storage;
- успешное обновление.

Если фотография отсутствует, используется fallback avatar, например инициалы пользователя.

В production загрузка выполняется через Backend.

В UI не отображляются детали объектного хранилища.

# 14. Products

Маршрут:

    /products

Просмотр каталога товаров.

## Header страницы

Содержит:

- заголовок `Товары`;
- количество записей;
- поиск.

Для `ADMIN`:

- кнопку `Добавить товар`.

## Таблица

Колонки:

- SKU;
- Название;
- Категория.

Для `ADMIN` дополнительно:

- Действия.

Действия:

- Редактировать;
- Удалить.

## Поиск

Поиск поддерживает:

- SKU;
- название.

## Empty state

Если товаров нет:

    Товары пока не добавлены.

Для `ADMIN`:

    Добавьте первый товар или импортируйте данные.

## Ошибка

При ошибке загрузки отображается Error State с действием повторной загрузки.

## Создание

# 17. CSV Import

Маршрут:

    /sales/import

Доступ:

    ADMIN

## Назначение

Массовая загрузка исторических продаж.

## Блок загрузки

Содержит:

- drag-and-drop область;
- выбор файла;
- описание формата;
- ограничение размера.

## Формат

Минимальный ожидаемый формат:

    product_sku
    date
    quantity

## Перед запуском

Отображаются:

- имя файла;
- размер;
- возможность заменить файл;
- кнопка `Импортировать`.

## Состояние выполнения

Во время операции:

- повторная отправка блокируется;
- отображается progress / loading state;
- пользователь понимает, что операция продолжается.

## Результат

Summary содержит:

- всего строк;
- импортировано;
- пропущено;
- ошибок.

При наличии ошибок строк отображаются:

- номер строки;
- код;
- описание.

# 18. Forecast Creation

Маршрут:

    /forecasts/new

## Назначение

Запуск прогнозирования спроса.

Это один из ключевых экранов системы.

## Форма

### Товар

Обязательный выбор.

Отображаются:

- название;
- SKU.

### Горизонт прогнозирования

Обязательный параметр.

Frontend ограничивает ввод допустимым диапазоном после фиксации технических ограничений модели.

## Контекст данных

До запуска желательно показать:

- выбранный товар;
- диапазон доступной истории;
- количество исторических наблюдений.

## Основное действие

    Построить прогноз

## Состояние выполнения

Во время прогнозирования:

- повторная отправка блокируется;
- отображается отдельное вычислительное состояние;
- пользователь понимает, что выполняется ML-операция.

## Ошибки

Отдельно обрабатываются:

- товар не выбран;
- некорректный горизонт;
- недостаточно данных;
- ML-сервис недоступен;
- ошибка прогнозирования.

---

Колонки:

- Дата;

При наличии фактических данных:

- Факт;
- Отклонение.

## Действия

- Новый прогноз;
- Вернуться к истории.

# 21. Users Management

Маршрут:

    /admin/users

Доступ:

    ADMIN

## Назначение

Просмотр и административное управление учётными записями.

Страница не используется для редактирования персональных данных пользователя.

Администратор не должен через этот интерфейс изменять:

- имя;
- email;
- фотографию.

Пользователь управляет этими данными через собственный Profile.

## Таблица пользователей

Основные данные:

- avatar;
- имя;
- email;
- подразделение;
- должность;
- роль;
- статус.

## Поиск

Поиск может учитывать:

- имя;
- email;
- подразделение;
- должность.

## Статусы

Используются:

    ACTIVE
    BLOCKED

В интерфейсе:

    Активен
    Заблокирован

Заблокированный пользователь должен визуально отличаться, но цвет не является единственным признаком состояния.

# 22. Редактирование пользователя ADMIN

Редактирование выполняется через Modal / Overlay или другое существующее компактное представление.

## Контекст

Показываются:

- имя;
- email.

Они не являются редактируемыми административными полями.

## Подразделение

Select:

    Подразделение
    [ Отдел разработки ▼ ]

Допускается состояние:

    Не назначено

## Должность

Select:

    Должность
    [ Senior Developer ▼ ]

После выбора подразделения показываются только активные должности данного подразделения.

Если у пользователя уже назначена деактивированная должность, текущее значение должно оставаться видимым до изменения.

## Роль

Select:

    USER
    ADMIN

## Статус

Select:

    ACTIVE
    BLOCKED

# 23. Зависимость Department → Position в Users Management

Department и Position не являются независимыми полями.

Правило:

    Department
        ↓
    доступные Position

Порядок:

1. администратор выбирает подразделение;
2. интерфейс фильтрует должности;
3. администратор выбирает должность;
4. сохраняется выбранная должность.

Если администратор изменяет подразделение и текущая должность не принадлежит новому подразделению:

- текущая должность сбрасывается;
- требуется выбрать новую.

Frontend не должен позволять сформировать комбинацию:

    Отдел маркетинга
    Senior Developer / Отдел разработки

Backend дополнительно проверяет это правило.

# 24. Ограничения административного редактирования

Администратор не может:

- заблокировать самого себя;
- изменить собственную роль `ADMIN` на `USER`;
- заблокировать последнего активного администратора;
- изменить роль последнего активного администратора на `USER`.

При попытке запрещённой операции интерфейс должен показать конкретную причину.

Например:

    Нельзя заблокировать последнего активного администратора.

или:

    Нельзя изменить роль последнего активного администратора.

Кнопка сохранения не должна имитировать успешную операцию при Backend-отказе.

- Добавить.

Нельзя создать должность:

# 31. Редактирование должности

Администратор может изменить:

- название;
- подразделение;
- статус активности через соответствующее действие.

При изменении подразделения должности необходимо учитывать существующие назначения пользователей.

Если Backend запрещает перенос назначенной должности:

- форма не закрывается как успешно сохранённая;
- пользователь получает понятное сообщение;
- существующие данные остаются без изменений.

---

# 32. Деактивация справочников

Деактивация не является удалением.

Если Department или Position уже используются пользователями:

- существующее назначение сохраняется;
- значение остаётся отображаемым;
- значение не предлагается для нового назначения.

Деактивированная должность, уже назначенная пользователю, может отображаться с пометкой:

    Неактивно

Администратор должен иметь возможность заменить такое назначение активным.

# 35. Loading states

Для каждой сетевой или длительной операции существует loading state.

## Начальная загрузка

Для таблиц используются:

- skeleton;
- placeholder rows;
- другой согласованный loading pattern.

## Отправка формы

Основная кнопка:

- блокируется;
- показывает состояние выполнения.

## Avatar

При загрузке фотографии:

- повторная загрузка блокируется;
- текущий профиль остаётся доступным;
- ошибка загрузки не должна визуально уничтожать существующую фотографию до успешной замены.

## Forecast

Вычислительная операция должна иметь отдельную понятную обратную связь.

# 36. Empty states

Empty State должен:

- объяснять отсутствие данных;
- при возможности предлагать следующее действие.

Примеры:

### Нет товаров

    Товары пока не добавлены.

### Нет продаж

    История продаж пока отсутствует.

### Нет прогнозов

    Вы ещё не создавали прогнозы.

### Нет пользователей по фильтру

    Пользователи по выбранным условиям не найдены.

### Нет подразделений

    Подразделения пока не созданы.

Для ADMIN:

    Добавить подразделение

### Нет должностей

    Должности пока не созданы.

### Нет результатов фильтрации

    По выбранным условиям ничего не найдено.

Пустой экран без объяснения не допускается.

# 37. Error states

Ошибки разделяются на:

- ошибки формы;
- ошибки загрузки;
- ошибки доступа;
- ошибки Backend;
- ошибки ML;
- ошибки Object Storage;
- конфликт административной операции;
- отсутствие ресурса.

## Ошибка формы

Отображается рядом с проблемным полем или другим однозначным способом.

## Ошибка загрузки страницы

Содержит:

- понятное описание;
- `Повторить`.

## Access Denied

Состояние:

    Недостаточно прав для выполнения операции.

## Not Found

Состояние:

    Запрашиваемый объект не найден.

## Administrative Conflict

Пример:

    Нельзя заблокировать последнего активного администратора.

## Organization Conflict

Пример:

    Должность назначена пользователям и не может быть перенесена в другое подразделение.

# 40. Responsive behaviour

Основной целевой формат:

    Desktop / Laptop

При уменьшении ширины:

- Sidebar сворачивается;
- формы становятся одноколоночными;
- таблицы получают горизонтальную прокрутку или адаптивное представление;
- карточки перестраиваются;
- графики используют доступную ширину;
- модальные окна не выходят за viewport.

Users Management и Organization должны оставаться функциональными на меньшей ширине.

Критические административные действия нельзя скрывать только из-за размера экрана.

# 41. Ограничения первой версии интерфейса

В рамках MVP не требуется:

- сложная персонализация Dashboard;
- drag-and-drop настройка Dashboard;
- пользовательские темы;
- мобильное приложение;
- встроенный редактор ML-модели;
- управление обучением модели;
- сложное дерево организационной структуры;
- модель руководителей и подчинённых;
- отдельная система ACL;
- история изменения ролей;
- история кадровых перемещений;
- временная блокировка аккаунта;
- синхронизация оргструктуры с ERP / HR-системой.
